# Kasm Agent Operator

## What this chart installs

* The CustomResourceDefinitions the operator owns: `agents`, `kasmworkspaces`, and
  `kasmimagepullers` in the `agent.kasm.com` group.
* The cluster RBAC the operator needs (`manager-role` and its binding, the namespaced
  `leader-election-role`, and the metrics authn/authz roles), plus the `kasm-agent` and
  `kasm-nginx-sidecar` ClusterRoles that the operator binds to at runtime.
  The ClusterRole grants no access to Secrets: the per-workspace storage-mapping Secret is read, created and
  updated by name inside the namespace that holds the Agent, and that permission is a namespaced Role the
  [kasm-agent-instance](../kasm-agent-instance/README.md) chart stamps wherever it installs an Agent
  (`operatorRBAC.*`). This needs an operator build that no longer caches Secrets (2026-09-08 or later).
* The `controller-manager` ServiceAccount and the operator Deployment that reconciles the custom
  resources above.

This chart is normally consumed as a subchart of the `kasm-agent` umbrella chart, under the alias
`operator`, so its values are set beneath an `operator:` key there. It also installs standalone.

**Chart-managed RBAC reverts manual edits.** `manager-role` and the other RBAC objects here are ordinary chart manifests, so any `helm upgrade` re-applies them and undoes hand edits — including a rule removed with `kubectl patch`. That is the intended behaviour, but it matters when testing the operator under reduced permissions: change the Agent CR with `kubectl` inside such a test window rather than `helm upgrade`, and confirm effective permissions with a SubjectAccessReview that includes the ServiceAccount's groups (`kubectl auth can-i ... --as=system:serviceaccount:<ns>:controller-manager --as-group=system:serviceaccounts --as-group=system:serviceaccounts:<ns> --as-group=system:authenticated`).

## This chart is a cluster singleton

Two of the ClusterRoles it ships, `kasm-agent` and `kasm-nginx-sidecar`, are deliberately **not**
templated or release-prefixed. When the operator reconciles an `Agent` custom resource it creates
bindings that reference those ClusterRoles by those exact names, and `manager-role` grants the operator
`bind` on exactly those two `resourceNames`. The same is true of the other RBAC objects, which keep the
fixed names used by the operator's kustomize deployment (`manager-role`, `manager-rolebinding`,
`leader-election-role`, `metrics-auth-role`, `metrics-reader`) so that a cluster converting from
kustomize to Helm keeps the same objects.

The practical consequence: **install only one release of this chart per cluster.** A second release in
another namespace will fight the first one for ownership of those cluster-scoped objects.

## CustomResourceDefinition lifecycle

There are two supported ways to get these five CRDs onto a cluster, and one supported way to change them
afterwards. Pick the pair that matches how the fleet is run; they interoperate.

### 1. This chart's `crds/` directory — the default, and what makes a one-command install work

The CRDs live in `crds/`. Helm installs them **before** rendering and validating the release manifest —
required, because the umbrella chart creates `Agent` and `KasmImagePuller` resources in the same release,
and install-time validation would otherwise reject those kinds as unknown. The trade-offs of the `crds/`
mechanism apply:

* `helm install` creates the CRDs if they are absent (use `--skip-crds` to opt out).
* `helm upgrade` **never touches them**. See the two upgrade paths below.
* `helm uninstall` leaves the CRDs, and every custom resource stored in them, in place.

### 2. The `kasm-agent-crds` release — Helm-native CRD upgrades

[`charts/kasm-agent-crds`](../kasm-agent-crds) ships the same five CRDs as ordinary templates, so a
release of *that* chart owns their lifecycle and `helm upgrade` applies schema changes like any other
resource. Install it **before** `kasm-agent` or `kasm-platform` on a fresh fleet, and upgrade it before
them thereafter; its `helm.sh/resource-policy: keep` annotations mean uninstalling it never deletes a CRD
or a stored custom resource. This is the path for fleets that want CRD versions moving through the same
review and rollout machinery as the rest of their Helm estate.

It is additive, not exclusive: the `crds/` directory above still ships in this chart, and Helm skips a CRD
that already exists rather than replacing it. A cluster whose CRDs arrived through `crds/` can be adopted
into a `kasm-agent-crds` release by labelling and annotating them first — that chart's README has the
exact procedure, and the rollback warning that goes with owning schemas in a release.

### 3. `kubectl apply --server-side` — the side channel, always valid

Whether or not the `kasm-agent-crds` release is in play, applying the files by hand upgrades the schemas
on an existing cluster:

```console
kubectl apply --server-side -f charts/kasm-agent-operator/crds/
```

This stays the documented upgrade path for any cluster not running a `kasm-agent-crds` release.

### Where the schemas come from

The CRD files are copied verbatim from `config/crd/bases/` in the `kasm-agent-operator` repository, plus a
comment header. To pick up a schema change, regenerate them upstream with `make manifests` and re-copy the
file bodies — into **both** `crds/` here and `charts/kasm-agent-crds/templates/`. `make crds-sync-check`
fails the build if the two copies disagree.

## Telemetry

With `otel.enabled` (the default) the operator container gets `OTEL_EXPORTER_OTLP_ENDPOINT` and
`OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=cumulative`. The endpoint defaults to
`http://<release>-kasm-otel-collector:4318`, the collector the `kasm-agent` umbrella chart deploys
alongside this subchart; set `otel.endpoint` to point at a collector of your own.
