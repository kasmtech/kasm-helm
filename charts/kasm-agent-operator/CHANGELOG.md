# Changelog

All notable changes to the kasm-agent-operator chart are documented here.

## [Unreleased]

### Changed
- `Agent` gains `spec.seccompInstaller`, a per-agent seccomp-profile installer DaemonSet the operator deploys when the field is set. The chart ships a `kasm-seccomp-installer` ClusterRole (`configmaps` get/list/watch) and grants the operator `bind` on it in `manager-role`, so the operator can create the per-Agent RoleBinding without holding the permission itself (`apps/daemonsets` was already granted). The installer follows the Agent's `workspacesNodeSelector`/`workspacesTolerations`. The chart carries the schema and the RBAC.
- CRDs synced from the operator (image-puller consolidation): `Agent` gains `spec.imagePuller` (`enabled`, `refreshIntervalSeconds`, `extraImages`, `resources`) and `KasmImagePuller` gains `spec.refreshIntervalSeconds`, so a single puller per agent — maintained from the manager's catalog plus any pre-seed extras, re-pulling mutable tags on the interval — replaces the separate manager-driven and chart-rendered pullers.
- CRDs synced from the operator (2026-09-15, image-puller rollout gating): `KasmImagePuller.status.summary` gains `imagesPending`, and the spec descriptions state the operator's new rollout rule. A change to the image set is a new DaemonSet pod template, and the kubelet finishes a replaced puller pod's remaining pulls before it honours the deletion, so every rollout that landed mid-pull stacked another pod per node pulling the same images. The operator now applies a template change only once no puller pod is still pulling; images added or removed in the meantime accumulate and go out together, the CR reports `Progressing=True` with reason `RolloutDeferred` while it waits, and a pull that has given up (`ImagePullBackOff`) does not hold it. The image list is staged sorted, so a reordered catalog is not a rollout, and the DaemonSet's `maxSurge` is `100%` so nodes roll in parallel instead of one at a time. The chart carries only the schema.
- CRDs synced from the operator (2026-09-15, image-puller back-off bookkeeping): `KasmImagePuller.status.nodeBackoffs[]` gains `lastEvictedPodUID`, and the descriptions no longer promise that the puller's back-off excludes nodes through its DaemonSet pod template. That exclusion is gone: every change to the back-off list rolled the DaemonSet and aborted the pulls in flight on all nodes. The kubelet's own admission and the DaemonSet controller's back-off cover a node under pressure; `status.nodeBackoffs` stays as bookkeeping.
- CRDs synced from the operator (2026-09-15, server labels and workspace tolerations): `Agent` gains `spec.labels` (server labels advertised in every heartbeat) and `spec.workspacesTolerations` (tolerations for every workspace pod, also scoping the agent's puller and capacity report); `KasmWorkspace.status` and `KasmImagePuller.status.nodeBackoffs[]` gain `lastOOMKilledAt`, the termination time of the last OOM kill already counted, so a container that restarts before the next reconcile is still counted once.
- `manager-role` grants `get`, `list` and `watch` on `nodes` instead of `get` alone. The operator reads a Node through controller-runtime's cached client when an eviction/OOM back-off window closes, and that client starts a Node informer on first use; with `get` only the informer's list was forbidden, the read never returned, and every workspace whose window had just closed stayed `Pending` with its replacement pod `Running` until the operator was restarted.
- The controller-manager pod template now carries the `kasm.com/security` and `kasm.com/healthcheck` annotations unconditionally. They are the markers this repository's Kyverno gates key off, and without them the operator Deployment was skipped by the workload-hardening and probe policies entirely — it was only ever checked for host namespaces. The pod and container securityContexts gain the fields those gates require and the Deployment did not state: `fsGroupChangePolicy: OnRootMismatch` on the pod (a no-op, since no `fsGroup` is set), and `runAsNonRoot: true` plus `seccompProfile.type: RuntimeDefault` restated at container scope, where the pod-level values already applied. No runtime behavior changes.
- `kasm-nginx-sidecar` ClusterRole now also grants `services` get/list/watch, mirroring the operator repo's regenerated `nginx_sidecar_clusterrole.yaml`: the sidecar watches a session's workspace Service directly instead of polling DNS, which raced the Service record's own propagation. Reads only; the role still grants no write verb on anything.
- `manager-role` no longer grants any access to Secrets. The operator only ever reads, creates and updates the per-workspace storage-mapping Secret by name, so that access is granted per namespace by the `kasm-agent-instance` chart (`operatorRBAC.*`) wherever an Agent is installed.
- `manager-role` ClusterRole narrowed to match the operator, which does not cache Secrets: `secrets` is get/create/update only (no list, watch, patch, delete), `persistentvolumes` and `clusterrolebindings` drop list/watch (and patch), `rolebindings` drops delete. Every other rule is unchanged.
- CRDs updated from the operator (2026-09-04): `Agent` gains `spec.sessionProxy.otel.endpoint` (session-proxy sidecar OTLP endpoint override; empty disables the exporter), and `KasmWorkspace.spec.fileMappings[]` gains `binaryData` (binary file content, mirrors a ConfigMap's `binaryData`) and `writable` (copy-on-start so the session user can edit the file).
- README lists all five CRDs it owns, adding `warmpools` and `warmpoolinstances` in `pools.kasm.ai`; the regeneration hint says `make readme-all`; the first section links the docs index. The HTML values-table template moved to the shared `_templates.gotmpl`.

### Added

- Initial release: installs the `agent.kasm.com` CustomResourceDefinitions, the static cluster RBAC the operator and the workloads it reconciles require, and the controller-manager Deployment.
