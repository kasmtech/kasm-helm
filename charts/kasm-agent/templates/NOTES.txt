SESSION PROXY TLS

  agent.sessionProxy.certificate.enabled is false, so this chart does not issue a certificate for
  the session proxy. The TLS Secret must already exist in namespace "{{ .Release.Namespace }}", of type
  kubernetes.io/tls, {{ if $certSecret }}named "{{ $certSecret }}"{{ else }}with its name set in agent.sessionProxy.certSecretName{{ end }}.

  Create it from an existing certificate:

    kubectl create secret tls {{ $certSecret | default "<agent.sessionProxy.certSecretName>" }} \
      --namespace {{ .Release.Namespace }} \
      --cert=path/to/tls.crt --key=path/to/tls.key

  Or set agent.sessionProxy.certificate.enabled=true, along with
  agent.sessionProxy.certificate.issuerRef and agent.sessionProxy.certificate.dnsNames, to have
  cert-manager issue and renew it. Browsers connect to the session proxy directly, so the
  certificate must be trusted by the client, not just by the cluster.

{{- if and $storageMappings (not $csiRcloneEnabled) }}
WARNING: agent.storageMappings.enabled is true but csiRclone.enabled is false.

  Cloud storage mappings are provisioned through the rclone CSI driver
  (rclone.csi.veloxpack.io). Unless that driver is already installed in this cluster by something
  else, workspace pods with a storage mapping will stay Pending with an unbound PVC. Either set
  csiRclone.enabled=true, or install the driver separately. Nodes also need the FUSE kernel module
  for rclone mounts to work.

{{ end }}
{{- if and $videoEnabled (not (and $nodePrepEnabled $v4l2)) }}
WARNING: videoDevicePlugin.enabled is true but v4l2loopback node preparation is not.

  The device plugin only advertises /dev/video* devices that already exist on a node. With no
  v4l2loopback module loaded, and no physical capture devices on the nodes, it will advertise zero
  devices and every webcam-enabled workspace will fail to schedule. Set nodePrep.enabled=true and
  nodePrep.modules.v4l2loopback.enabled=true, or confirm the nodes provide real video devices.

{{ end }}
{{- if and $gpuOperatorEnabled (not $agentGpu) }}
WARNING: gpuOperator.enabled is true but agent.gpu.enabled is false.

  The GPU Operator will advertise nvidia.com/gpu on GPU nodes, but the agent will not request it,
  so no workspace ever lands on a GPU. Set agent.gpu.enabled=true — it sets
  KASM_GPU_OPERATOR_ENABLED on the agent, which is what makes it schedule GPU workspaces against
  the advertised resource.

{{ end }}
{{- if $nodePrepEnabled }}
WARNING: nodePrep.enabled is true — this release runs privileged pods.

  Node preparation builds and loads host kernel modules, so its DaemonSet runs privileged, with
  host PID and mounts from the host filesystem. Namespace "{{ .Release.Namespace }}" must permit the
  "privileged" Pod Security Standard:

    kubectl label namespace {{ .Release.Namespace }} pod-security.kubernetes.io/enforce=privileged

  Kernel headers matching the running kernel must be available on each node, and on nodes with
  Secure Boot enabled the built modules must be signed with an enrolled MOK key
  (nodePrep.secureBoot.existingMokSecret). Restrict which nodes are prepared with
  nodePrep.nodeSelector.

{{ end }}
{{- if .Values.networkPolicies.enabled }}
NOTE: networkPolicies.enabled is true.

  Baseline NetworkPolicies were created in namespace "{{ .Release.Namespace }}", starting with a default deny.
  They do nothing at all unless this cluster's CNI enforces NetworkPolicy — Calico, Cilium, Antrea,
  and the managed equivalents do; plain kubenet and some managed CNIs silently ignore every policy.
  Confirm enforcement before treating this as isolation:

    kubectl get networkpolicies -n {{ .Release.Namespace }}

  The defaults for networkPolicies.apiServer.cidr, networkPolicies.manager.cidr, and
  networkPolicies.otelBackend.cidr are 0.0.0.0/0 on specific ports. Narrow them to the real
  destinations once known.

{{ end }}
