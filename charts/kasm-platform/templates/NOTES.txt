SESSION TRAFFIC IS RELAYED THROUGH THE CONTROL PLANE. Nothing more to configure.
--------------------------------------------------------------------------------

  Browsers only ever talk to the control plane; its proxy connects to the session proxy inside
  the cluster, at

    {{ $effectivePublic }}:{{ $effectivePublicPort }}

  The zone keeps its seeded default of proxied connections, the Kasm Authorization Domain stays
  at its default, and the session proxy's self-signed certificate is never shown to a browser.

  To have browsers connect to the session proxy DIRECTLY instead (no relay hop), do all three:

    1. Publish the session proxy at a public hostname under the SAME parent domain as the control
       plane, and set kasm-agent.agent.publicHostname to it - together with one of
       kasm-agent.agent.ingress / httpRoute / route / tlsRoute / gatewayRoute, and a certificate
       browsers trust.
    2. Scope the session cookie to that shared parent domain: kasm-helm.kasmConfig.authDomain on
       a fresh install, or Settings -> Auth -> Kasm Authorization Domain in the admin UI on an
       existing database. Otherwise every session connection fails with a 401.
    3. Switch the zone to direct connections. On a fresh install, preseed it:

         kasm-helm:
           kasmConfig:
             generatePreseed: true
           kasmZones:
             - name: {{ $agentZone }}
               proxy_hostname: <control-plane hostname>
               proxy_connections: false
               upstream_auth_address: <control-plane hostname>

       On an existing control plane the preseed no longer runs - change Proxy Connections and
       Upstream Auth Address under Infrastructure -> Zones.

================================================================================
DIRECT SESSION CONNECTIONS - three things to check
================================================================================

  Browsers will connect to the session proxy at {{ $effectivePublic }} directly, so the control plane
  and the agent have to agree on more than the manager address.
{{- if $authDomain }}

  1. THE AUTH DOMAIN - seeded at database initialization. Nothing to do on a fresh install.
     kasm-helm.kasmConfig.authDomain is set to {{ $authDomain }}, so the Kasm Authorization Domain was
     written into the seed before the database came up. The session cookie is scoped to
     {{ $authDomain }} and reaches both {{ $publicAddr | default "<publicAddr>" }} and {{ $effectivePublic }}.

     Confirm both hostnames really are under {{ $authDomain }} - a mismatch still 401s. This only
     applies to a database this release initialized; on an EXISTING database the seed never ran,
     so change it under Settings -> Auth in the admin UI, or through the admin API:

       POST /api/authenticate            {"username":"{{ $adminUser }}","password":"..."}   -> token
       POST /api/admin/get_settings      {"username":"...","token":"..."}                   -> setting_id of kasm_auth_domain
       POST /api/admin/update_setting    {"username":"...","token":"...","setting_id":"...","value":"{{ $authDomain }}"}
{{- else }}

  1. THE AUTH DOMAIN - MANUAL STEP REQUIRED after the first install.
     The Kasm Authorization Domain starts at its $request_host$ default. That scopes the session
     cookie to the control plane's hostname, the browser never sends it to the session proxy, and
     every session connection fails with a 401. Set it to the parent domain covering BOTH
     {{ $publicAddr | default "<publicAddr>" }} and {{ $effectivePublic }}: under Settings -> Auth in the admin UI, or
     through the admin API:

       POST /api/authenticate            {"username":"{{ $adminUser }}","password":"..."}   -> token
       POST /api/admin/get_settings      {"username":"...","token":"..."}                   -> setting_id of kasm_auth_domain
       POST /api/admin/update_setting    {"username":"...","token":"...","setting_id":"...","value":"<parent domain>"}

     On a FRESH install, set kasm-helm.kasmConfig.authDomain instead and it is seeded at database
     initialization.
{{- end }}

  2. THE ZONE MUST USE DIRECT CONNECTIONS.
     The seeded zone defaults route session traffic through the control-plane proxy, which 404s
     behind host-routing ingress. On a fresh install, preseed the zone:

       kasm-helm:
         kasmConfig:
           generatePreseed: true
         kasmZones:
           - name: {{ $agentZone }}
             proxy_hostname: {{ $publicAddr | default "<publicAddr>" }}
             proxy_connections: false
             upstream_auth_address: {{ $publicAddr | default "<publicAddr>" }}

     On an existing control plane the preseed no longer runs - change Proxy Connections and
     Upstream Auth Address under Infrastructure -> Zones.

  3. HOSTNAMES. The session proxy needs a certificate browsers trust for {{ $effectivePublic }}
     (kasm-agent.agent.sessionProxy.certificate, or a pre-created Secret), and a route to it
     (kasm-agent.agent.ingress / httpRoute / route / tlsRoute).
