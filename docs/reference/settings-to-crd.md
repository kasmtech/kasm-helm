# Reference: Kasm settings → agent custom resource fields

The engineer's companion to [**What works on Kubernetes**](../feature-matrix.md). That page answers
"does this feature work, and what do I need?". This one answers "where does this setting go?".

It walks the configuration surface of a **Kasm Workspaces 1.19.0** control plane — every column of
a Workspace (the `images` table), every group and session toggle (`group_settings`), and every
global setting (`settings`) — and names what carries each one when the session is a pod instead of
a Docker container.

The contract between the two halves is the `KasmWorkspace` custom resource: the agent turns a
launch request into one CR, and the operator reconciles that CR into a Deployment, a Service, and
whatever volumes, policies and lifecycle hooks the fields ask for. A setting with no field on the
CR does not reach the cluster at all — which is not the same as being broken. Most of the
catalogue is control-plane state that was never the runtime's business.

Values are written as they are set on the **`kasm-agent`** umbrella (`agent.*` is the
`kasm-agent-instance` subchart, `nodePrep.*` is `kasm-node-prep`, and so on). Under
[kasm-platform](../../charts/kasm-platform/README.md), prefix them with `kasm-agent.`.
Control-plane values keep their `kasm-helm.` prefix as they are set from `kasm-platform`; drop it
when installing [kasm-helm](../../charts/kasm-helm/README.md) directly.

## 1. Workspace (image) settings

| Setting(s) | On Kubernetes this becomes | Notes |
| ---------- | -------------------------- | ----- |
| **Catalog & presentation** — `name`, `friendly_name`, `description`, `image_src`, `categories`, `hidden`, `enabled`, `available`, `notes`, `hash`, `uncompressed_size_bytes`, `session_banner_id`, `session_banner_force_disabled`, `link_url`, `image_type`, `server_id`, `server_pool_id`, `restrict_to_server` | Nothing. Control-plane state that never leaves the manager. | The catalogue lives in the control-plane database; the cluster only ever sees the one workspace being launched. `image_type` is the fork in the road — only **Container** workspaces become pods. **Server** and **Server Pool** target a VM or physical host brokered over RDP/SSH/VNC, and **Link** is a bookmark; none of the three involve the agent, which is why `server_id`, `server_pool_id` and `restrict_to_server` have no Kubernetes counterpart. `hash` and `uncompressed_size_bytes` describe the image, not the pod; `available` is the manager's view of whether the image is staged, which the image puller feeds. `kasm-helm.kasmConfig.config` (with `kasm-helm.kasmConfig.generatePreseed=true`) can seed the whole catalogue at database initialisation — fresh installs only. (`image_id`, `created_at` and `updated_at` are database bookkeeping and appear nowhere else.) |
| **Compute sizing** — `cores`, `memory_bytes`, `x_res`/`y_res` | `spec.resources` on the `KasmWorkspace` | The agent fills the CR's resource requirements from the workspace's `cores` and `memory_bytes`, and the operator passes them to the Deployment. `x_res`/`y_res` are display geometry inside the session, not a Kubernetes resource — they arrive with the desktop environment variables the operator injects. Size memory honestly: the per-session `/dev/shm` `emptyDir` is memory-backed, so it counts against the pod's memory limit and toward node pressure ([node best practices](../../charts/kasm-agent/README.md#workspace-node-best-practices)). |
| **CPU allocation method** — `cpu_allocation_method` (Inherit / Shares / Quotas), global `images/default_cpu_allocation_method` | `cores` → `spec.resources` CPU. **Shares** (and *Inherit* under the default) sets a CPU **request only** — burstable, no ceiling (the Docker `cpu-shares` analogue). **Quotas** sets the CPU request **and an equal CPU limit** — a hard cap (the `cpu-quota` analogue). Memory (`memory_bytes`) always sets both request and limit. | Observed on a live session: Shares/Inherit → `requests.cpu=1`, no `limits.cpu`; Quotas → `requests.cpu=1` and `limits.cpu=1`; memory `1536Mi` request+limit in all cases. There is no oversubscription mode beyond those two — Kubernetes has no share weighting. The chart's node guidance arrives at the same place from the node side: leaving a workspace without a CPU limit is what reproduces Kasm's default Shares behaviour, "only throttled if there is CPU contention" ([node best practices](../../charts/kasm-agent/README.md#workspace-node-best-practices)). Re-verified on a 1.1200.0-develop control plane with the same agent build: Quotas → `requests.cpu=2` and `limits.cpu=2` — the mapping is agent-side and unchanged across manager versions. |
| **Image source & registry credentials** — `docker_registry`, `docker_user`, `docker_token` | `docker_registry` is honored as the image reference **only when the image name itself carries the registry host** (e.g. `registry.gitlab.com/...`). Per-image `docker_user`/`docker_token` **are** materialized by the agent into a per-registry `kubernetes.io/dockerconfigjson` Secret (`kasm-registry-<registry-host>`, scheme and `/v1/` stripped) and updated in place when the credentials change. Chart-level `agent.workspaceImagePullSecrets` (every workspace pod) and `agent.imagePuller.images[].imagePullSecrets` (pre-pulls) still apply for fleet-wide registries. | Verified on live sessions against a 1.1200.0-develop control plane: a `registry.gitlab.com` image with a valid deploy token launched with Secret `kasm-registry-registry-gitlab-com` generated and referenced from `spec.imagePullSecrets`; flipping the user updated that Secret in place, and restoring it re-synced it. Residual gaps: (1) for a Docker-Hub-style image name (`kasmweb/doom:develop`) with `docker_registry: https://kcr.kasmweb.com/v1/`, the Kubernetes agent pulls from Docker Hub and creates `kasm-registry-kcr-kasmweb-com` **without attaching it** — the `docker_registry` setting is not applied to the image reference, so a registry-scoped private image would fail to pull; (2) Secrets are not garbage-collected — an old-name `kasm-registry-https-…` Secret from before the naming fix stays behind. Test note: writing `docker_token` by direct SQL stores plaintext in an encrypted column and makes `request_kasm` return HTTP 500 — a test artifact, not a product path; set credentials through the UI/API. See the [private registries how-to](../howto/private-registries-and-image-pulling.md). |
| **Run / exec / launch configuration** — `run_config`, `exec_config`, `launch_config`, group `run_config` | The subset of Docker run options that has a `KasmWorkspace` field | `run_config` is a Docker `create`/`run` payload and only part of it survives translation. Honoured, because the CR has a field for each: `shmSize` (`shm_size`), `devices`, `securityContext` (`cap_add`, `privileged`), `command` and `args`, `env`, `annotations` and `labels`, `stopTimeoutSeconds`, `healthCheck` (overrides the default TCP probes), `imageMounts`, `initContainer`, and `podOverrides` as the escape hatch for anything else expressible as a pod-spec patch. `exec_config` becomes `podStartCommands`/`podStopCommands`. Docker-only keys — `network_mode`, `ulimits`, `hostname`, `dns`, restart policy, `pid_mode` and the rest — have no equivalent and have no effect: they are host-runtime concerns the pod sandbox owns. `imageMounts` needs the ImageVolume feature (Kubernetes 1.35+), with no host-unpack fallback. |
| **Persistent profiles** — `persistent_profile_path`, `enforce_workspace_persistence`, group `allow_persistent_profile` | `spec.profiles` — a PVC mounted at the profile path | The CR field carries `mountPath`, `capacity`, `storageClass` and `persistent`; when `persistent` is true the PVC outlives the CR. Which access mode you need, why shared profiles force `ReadWriteMany`, and the in-cluster NFS fallback are in the [RWX storage how-to](../howto/rwx-storage-for-profiles.md). |
| **Volume mappings** — `volume_mappings`, group `volume_mapping` | `spec.volumeMappings` — `hostPath` volumes of type `DirectoryOrCreate` | The mapping itself works; scheduling is the limitation. Docker mounts a path on the one host it runs on, whereas an unpinned pod can land on a node where the path does not exist and fail its mount. Node targeting with `agent.workspacesNodeSelector` is the fix — [how-to](../howto/privileged-workloads-and-policies.md). |
| **User storage mappings** — group `allow_user_storage_mapping`, `max_user_storage_mappings`, `read_only_user_storage_mapping` | `spec.storageMappings` — an rclone CSI volume per remote | Both `csiRclone.enabled=true` and `agent.storageMappings.enabled=true`, always: the driver alone mounts nothing and the agent flag alone points at a driver that is not there. Credentials stay in a Secret and never appear in the CR. [how-to](../howto/cloud-storage-rclone-csi.md). |
| **File mappings** — the workspace and group file-mapping tables (no `images` column of their own) | `spec.fileMappings` — one ConfigMap per mapping (`data` or `binaryData`), `subPath`-mounted; writable ones are staged and copied in at start | Nothing to enable. The only ceiling is etcd's 1 MiB per ConfigMap, and `defaultMode` carries the permission bits. |
| **Network restriction** — `restrict_to_network` | `spec.networkPolicy` / `spec.networkPolicyRef` — a per-workspace NetworkPolicy | The operator stamps the per-workspace policy with no configuration, but a policy is inert unless the CNI enforces NetworkPolicy — under Flannel or canal alone every rule is a no-op that silently succeeds. The full rule set, the podSelector-versus-namespaceSelector story, and the missing per-workspace egress IP are in [Cluster infrastructure](#networking-and-access) · [how-to](../howto/network-policy-enforcement.md). |
| **Named-network selection** — `restrict_network_names`, `allow_network_selection` | Nothing. A pod has one CNI attachment and no name to choose from. | Docker named networks are an addressing construct; a NetworkPolicy is a filter, not a network, so network restriction cannot offer a user a list of networks to launch into. Live evidence: the Kubernetes agent reports an empty network list to the manager (`servers.docker_networks = {}`), so the network selector has nothing to offer. What is missing is a network-attachment model — Multus with a secondary CNI, or an equivalent — which the operator does not implement. |
| **Egress gateways** — `override_egress_gateways` | `spec.cniEgress` — opaque endpoint config surfaced to the CNI chain by pod annotation | The CR field is only the request; the node-side half is the chained-CNI shim that enters the session's netns and brings the tunnel up there. Node prerequisites, the graceful-versus-crash lifecycle, and the older `spec.vpnSidecar` alternative are in [Cluster infrastructure](#networking-and-access) · [how-to](../howto/egress-installer-node-prerequisites.md). |
| **Web filtering** — `filter_policy_id`, `filter_policy_force_disabled`, group `web_filter_policy` | The squid adapter inside the session pod, pointed at the session-proxy Service | The agent substitutes the session-proxy Service address for the Docker agent's runtime IP discovery, so nothing has to be set. Enforcement is application-layer and inside the pod, which is its limitation. |
| **Zone pinning** — `restrict_to_zone`, `zone_id`, group `allow_zone_selection` | The zone the `Agent` custom resource registers in | One agent release is one zone. `agent.zone` must name a zone that exists on the control plane (`kasm-helm.kasmZones`), and the manager then routes zone-restricted workspaces to the agents in that zone. Several zones means several agent releases, one per zone, each with its own `agent.publicHostname`. |
| **GPU** — `require_gpu`, `gpu_count`, `gpu_graphics_acceleration`, `gpu_video_encoding` | `nvidia.com/gpu` in the pod's resource limits, plus `spec.devices` for the DRI nodes | Compute (`require_gpu`, `gpu_count`) needs `gpuOperator.enabled=true` and `agent.gpu.enabled=true`; graphics acceleration (`gpu_graphics_acceleration`, the EGL/DRI path) needs the driver in the node image · [how-to](../howto/gpu-nodes.md). Allocation moves to kubelet's Device Plugin API, which is more robust than the Docker agent's own bookkeeping but removes the Kasm-level GPU metadata. `gpu_video_encoding` (NVENC) additionally needs the GPU driver stack present on the node and in the workspace image — unverified in this lab, which has no GPU nodes. |
| **Session time limit** — `session_time_limit`, and the group setting of the same name | Nothing. The manager expires the session and asks the agent to destroy it. | Expiry is control-plane bookkeeping; the agent's part is the destroy, which is the same pod deletion any stop performs. What the cluster contributes is the shutdown budget: `stopTimeoutSeconds` on the CR (default 300) sets the pod's grace period, extended by 30s where a stop hook has to finish first. |
| **RDP / RemoteApp** — `rdp_client_type`, `is_remote_app`, `remote_app_icon`, `remote_app_name`, `remote_app_program`, `remote_app_args` | The control plane's RDP gateways. These settings describe **Server** workspaces, not pods. | Both gateways ship as ordinary Deployments in the control-plane chart and are on out of the box (`kasm-helm.components.rdpGateway.enabled`, `kasm-helm.components.rdpHttpsGateway.enabled`); `kasm-helm.directRdpService.enabled=true` is only for native-client access. The targets are Windows or Linux hosts **outside** the cluster — the gateway brokers to them and nothing here schedules a pod. |

## 2. Group and session settings

`group_settings` is where nearly every session behaviour is decided, and most of it is negotiated
between the browser client, KasmVNC inside the workspace image, and the control plane — the
container runtime underneath is not part of that conversation. That is why so much of this section
reaches nothing in the cluster at all. The exceptions are the toggles that need a host device, a
durable place to put bytes, or an API the Kubernetes agent does not have.

| Setting(s) | On Kubernetes this becomes | Notes |
| ---------- | -------------------------- | ----- |
| **Audio** — `allow_kasm_audio`, `kasm_audio_default_on` | Nothing cluster-side. Audio rides the session connection. | Playback is captured inside the session container and streamed to the browser, so no host sound device has to exist on the node and no chart value is involved. |
| **Microphone** — `allow_kasm_microphone` | A PulseAudio relay started inside the session pod | The operator injects `PULSE_RUNTIME_PATH` and mounts the PulseAudio runtime at `/var/run/pulse`; the workspace image supplies the binary. |
| **Webcam** — `allow_kasm_webcam` | A `/dev/video*` device from `v4l2loopback`, requested as the extended resource `kasm.com/video` | The one media toggle that changes the node: a kernel module has to be loaded and re-loaded after every reboot, and a device plugin has to advertise the result. Both halves are required (`nodePrep.enabled=true` + `nodePrep.modules.v4l2loopback.enabled=true` + `videoDevicePlugin.enabled=true`), and the namespace has to permit the `privileged` Pod Security Standard. [how-to](../howto/kernel-modules-and-webcam.md). |
| **Clipboard** — `allow_kasm_clipboard_up`, `allow_kasm_clipboard_down`, `allow_kasm_clipboard_seamless` | Nothing cluster-side | Clipboard direction and seamless mode are client-and-image behaviour; the pod boundary is irrelevant to them. |
| **Uploads & downloads** — `allow_kasm_uploads`, `allow_kasm_downloads` | Nothing cluster-side | Transfers go over the session connection. Where the bytes land does matter: without a persistent profile or a storage mapping, an uploaded file lives on the pod's ephemeral filesystem and dies with the session. |
| **Printing** — `allow_kasm_printing` | CUPS started inside the session pod | Entirely in-pod; the stock Kasm images ship CUPS and `kasm_printer_service`. |
| **Gamepad** — `allow_kasm_gamepad` (with `control_panel.advanced_settings.show_game_mode`) | Nothing cluster-side | Gamepad input is relayed by the browser client into the session. Unlike the webcam it needs no host device node, so it costs nothing at the cluster layer. |
| **Session sharing & casting** — `allow_kasm_sharing`, `shared_session_full_control`, `lock_sharing_video_mode`, global `cast/*` | Extra viewers on the same session, through the same session proxy | Shared and cast viewers connect through the session-proxy Service the owner already uses, so sharing needs no exposure beyond the session proxy itself. Cast configurations are control-plane objects and can be seeded with `kasm-helm.kasmConfig.config`. |
| **Session recording** — `record_sessions`, with `session_recording/*` and `storage/object_storage_key`/`storage/object_storage_secret` | A recorder process in the session pod, uploading before the pod is allowed to terminate | Capture works and needs no values. The limitation is storage, not recording: an in-flight recording buffers on the pod's own storage, so an evicted or OOM-killed pod loses it. The stop hook holds the pod open for the upload within `stopTimeoutSeconds` + 30s. As built in the fixed operator: `KasmWorkspace.spec.recordingBufferSize` (default `3Gi`) provisions an `emptyDir` with that `sizeLimit` at `/opt/kasm/recordings`, a `recorder-prep` init container pre-creates it for the recorder user, and the container's ephemeral-storage request/limit is seeded to cover it — verified live by patching a workspace (`KASM_SVC_RECORDER=1`, `1Gi` → mount + `2Gi` ephemeral floor). It bounds the buffer and survives container restarts, not pod loss; the manager only enables the recorder when a recording upload location is configured **and the deployment is licensed for recording** — unlicensed, the API logs "Session recording is configured but not licensed" and the session starts with the recorder disabled. |
| **SSH key injection** — `inject_ssh_keys` | A ConfigMap mounted at `/home/kasm-user/.ssh/`, with permissions fixed by a start hook | Rides the file-mapping path, then `chown`s to `1000:0` and `chmod 400`s the private key. |
| **Container logging** — `enable_container_logging` (`enable_ui_server_logging` is control-plane-side and unaffected) | Nothing. The agent has no route to a container's logs. | The agent's ClusterRole (`kasm-agent`) grants `pods` get/list/watch but no `pods/log`, so the Kubernetes agent cannot fetch container logs through the API server the way the Docker agent reads `docker logs`. Workspace stdout/stderr is still available as ordinary pod logs (`kubectl logs`) and via the cluster's log pipeline (`otelCollector`), not through the Kasm UI. |
| **Environment variables** — `expose_user_environment_vars` | `spec.env` on the `KasmWorkspace` | User and group environment variables are merged with the desktop variables the operator injects and become ordinary container env. |
| **Stop & delete** — `allow_kasm_stop`, `allow_kasm_delete`, `allow_kasm_force_delete` | Deletion of the `KasmWorkspace`: stop hooks from a finalizer, then the Deployment, Service and policy go | Deleting the CR runs `podStopCommands` from a finalizer inside the grace period — which is what gives an in-flight recording its chance to upload — and then removes the workload. A persistent profile PVC survives the deletion; force delete skips the wait. |
| **Pause** — `allow_kasm_pause` | Nothing. The workspace pod keeps running. | Kubernetes has no container pause. Observed live: `pause_kasm` returns success and the manager marks the session *paused*, but the workspace pod is simply replaced and keeps running (`phase=Running`); `resume_kasm` then fails with "No resources are available to create the requested Kasm". Treat `allow_kasm_pause` as unsupported on the Kubernetes agent until the operator implements pause semantics (e.g. scale-to-zero + resume); disable it for groups that use Kubernetes agents. Re-tested on 1.1200.0-develop: identical pause behaviour (pod replaced and still running, manager shows *paused*), but `resume_kasm` now returns success — the 1.19.0 "No resources are available" resume error is gone; the session was simply never paused. |
| **Session lifecycle & limits** — `keepalive_expiration`, `keepalive_interval`, `keepalive_expiration_action`, `idle_disconnect`, `usage_limit`, `max_kasms_per_user`, `delete_anon_user_on_expiry_with_active_session` | Nothing. Manager-side accounting; the agent only ever receives a create or a destroy. | The timers run on the control plane, with global counterparts under `scale/*`. The cluster's contribution is the shutdown budget the operator gives a terminating session. |
| **RDP client toggles** — `allow_login_kasm_rdp`, `allow_kasm_rdp_client_file_transfer_clipboard`, `allow_kasm_rdp_map_local_drives`, `allow_kasm_rdp_webauthn_passthrough`, `allow_kasm_smart_card_passthrough` | The control plane's RDP gateways | These govern a native RDP client connecting to a **Server** workspace, not a container session, so they are settled entirely in the control-plane chart. |
| **Authentication & accounts** — `allow_totp_2fa`, `allow_webauthn_2fa`, `require_2fa`, `allow_2fa_self_enrollment`, `require_subscription`, `password_expires`, `auto_add_local_users`, `auto_login_to_kasm` | Nothing. Entirely control plane. | Identity is decided before a workspace exists, so none of it reaches the agent. SSO, LDAP and SAML configurations are seedable at database initialisation with `kasm-helm.kasmConfig.config`. |
| **UI & client preferences** — `control_panel.*`, `kasmvnc_mode_preference`, `enable_webp`, `default_ui_language`, `dashboard_redirect`, `default_image`, `show_disabled_images`, `disabled_image_message`, `display_ui_errors`, `session_banner`, `staged_session_language_and_timezone_preference_override`, `metadata`, `kasm_ime_mode_default_on` | Nothing cluster-side | Control-panel visibility, language, banners and error display are all UI state. `kasmvnc_mode_preference` and `enable_webp` select the streaming mode KasmVNC negotiates inside the session container — an image capability, unaffected by what runs the container. |

## 3. Global settings

The `settings` table is keyed by category and name — `auth/kasm_auth_domain`,
`scale/provision_timeout`, `logging/log_host`. Most categories are control-plane behaviour the
cluster never sees. The ones that matter here are the categories that describe *where the agent
is*, *what it may do*, and *who else is allowed to talk to it*.

| Setting(s) | On Kubernetes this becomes | Notes |
| ---------- | -------------------------- | ----- |
| **Manager & agent registration** — `manager/agent_version`, `manager/token`, `manager/manager_expiration`, `manager/same_zone_reply`, `proxy/proxy_path`, `scale/auto_agent` | The `Agent` custom resource: the agent registers with the manager, heartbeats, and is issued a `serverID` | Set with `agent.manager.hostname`, `agent.manager.port`, `agent.manager.scheme`, `agent.manager.pathPrefix`, `agent.manager.existingTokenSecret` (or `agent.manager.token`) and `agent.publicHostname`. This is the join between the two halves and the first thing to get right. The manager token is the shared secret both sides check — prefer `agent.manager.existingTokenSecret`, because a token set inline lands in the Helm release history. `agent.manager.pathPrefix` (`/manager_api` by default) is the client-side counterpart of `proxy/proxy_path`; set it empty only for direct manager-Service access. `manager/agent_version` gates which agent builds the manager accepts, so an image tag out of step with the control plane surfaces as a registration failure rather than a runtime error. |
| **Authorization domain & auth session** — `auth/kasm_auth_domain`, `auth/session_lifetime`, `auth/same_site` | The cookie scope the control plane hands the browser — which decides whether the session proxy's hostname is inside it | Set with `kasm-helm.kasmConfig.generatePreseed=true` and `kasm-helm.kasmConfig.authDomain`. The one auth setting with a genuinely Kubernetes-shaped consequence: the agent's session proxy is a **different hostname** from the control plane, so the session cookie has to be scoped to a domain that covers both or the browser drops it the moment streaming starts. Applied at database initialisation — fresh installs only; on an existing database change it in the admin UI under Settings → Auth. [how-to](../howto/external-access-and-tls.md). |
| **Zones & routing** — the zone objects and their `proxy_connections` / `upstream_auth_address` | One agent release per zone, each advertising its own session-proxy address | Set with `kasm-helm.kasmZones`, `agent.zone` and `agent.publicHostname`. Zones are how a multi-region deployment decides which agent a workspace launches on. Each `kasmZones` entry produces a zone in the control plane and, with `ingress` or `route` configured, its own external address; `agent.zone` on the agent side must match one of those names. |
| **Autoscaling** — `scale/*`: `auto_agent`, `guardian_*`, host and component expirations, `provision_timeout`, `keepalive_expiration`, `cleanup_orphaned_autoscale_servers`, `forward_inter_zone_agent_requests` | Nothing directly. These drive Kasm's VM-provider autoscaling, not pod scheduling. | Kasm's autoscale loop provisions *servers* from a cloud VM provider; on Kubernetes the node layer belongs to the Cluster Autoscaler or Karpenter and the session layer to the scheduler, so most of `scale/*` does not apply to this agent. What the operator does offer (`operator.enabled=true` installs the CRDs) is `WarmPool`/`WarmPoolInstance` — pre-warmed pods that cut cold-start latency, which is pre-warming rather than demand-driven scaling; no chart value creates one. The guardian and expiration timers still govern the agent's own liveness on the manager side. |
| **Session recording globals** — `session_recording/*`: `bitrate`, `framerate`, `res`, `retention`, `upload_location`, `object_storage_key`/`object_storage_secret`, `queue_length`, `guac_disk_limit` | Recorder parameters passed into the session pod | The parameters are honoured as they are on a Docker agent; the caveat is durability, because the recording buffers on the session pod's ephemeral storage until it uploads. `guac_disk_limit` applies to Guacamole/RDP recordings on the control plane, not to container sessions. As built in the fixed operator: `KasmWorkspace.spec.recordingBufferSize` (default `3Gi`) provisions an `emptyDir` with that `sizeLimit` at `/opt/kasm/recordings`, a `recorder-prep` init container pre-creates it for the recorder user, and the container's ephemeral-storage request/limit is seeded to cover it — verified live by patching a workspace (`KASM_SVC_RECORDER=1`, `1Gi` → mount + `2Gi` ephemeral floor). It bounds the buffer and survives container restarts, not pod loss; the manager only enables the recorder when a recording upload location is configured **and the deployment is licensed for recording** — unlicensed, the API logs "Session recording is configured but not licensed" and the session starts with the recorder disabled. |
| **Object storage** — `storage/object_storage_key`, `storage/object_storage_secret` | Credentials the control plane and the recorder use. No cluster object. | The bucket is reached from wherever the upload runs, so the only Kubernetes consideration is egress: if `networkPolicies.enabled=true`, the path out has to be permitted ([how-to](../howto/network-policy-enforcement.md)). |
| **Logging forwarding** — `logging/log_host`, `logging/log_port`, `logging/log_protocol`, `logging/hec_token`, `logging/url_endpoint`, log retention | The control plane's own forwarder — Splunk HEC, or a syslog/HTTP endpoint | Unchanged by Kubernetes: the manager ships its own logs wherever it is told to. The cluster-side path is a different pipeline entirely — operator, agent and session traces, metrics and Kubernetes events — and is `otelCollector.enabled=true`. |
| **Web filter globals** — the `filter/*` category and its policies | Policy definitions the session's squid adapter enforces in-pod | Policies are control-plane objects (`kasm-helm.kasmConfig.config` seeds `filter_policies` at database initialisation); enforcement happens inside the session pod, which is where its limitation lies. |
| **Connections** — the `connections/*` category: default `rdp`, `ssh` and `vnc` connection settings, including the `rdp_*` keys | Defaults for connections the gateways broker to hosts outside the cluster | These are the defaults a **Server** workspace inherits when a user connects to it; container sessions never use them. Reachability of the target hosts from the gateway pods is the only cluster concern. |
| **Image defaults** — `images/add_images_to_default_group`, `images/default_cpu_allocation_method` | Catalogue defaults applied when a workspace is created | `add_images_to_default_group` is pure control plane. `default_cpu_allocation_method` is the global behind the per-workspace CPU allocation row in [section 1](#1-workspace-image-settings) and inherits its caveat — the mode itself has no Kubernetes counterpart. |

## 4. Cluster infrastructure: implementation notes

What each cluster-side capability actually does, and what has to exist for it. The status and the
values that switch each one on live in [What works on Kubernetes](../feature-matrix.md); this is
the mechanism underneath.

### Sessions and media

| Feature | Cluster prerequisites | How it works |
| ------- | --------------------- | ------------ |
| **Core workspace (VNC/display)** | Any conformant cluster with containerd or CRI-O. No CNI requirement at this layer. · [how-to](../howto/node-tuning-and-swap.md) | The operator turns each `KasmWorkspace` into a single-replica Deployment plus a ClusterIP Service on 6901, injects the default desktop env vars, and mounts `/dev/shm` as a 2Gi memory-backed `emptyDir` (Kubernetes' own 64Mi default is not survivable for a browser). The session proxy must be reachable from the manager. |
| **Webcam (v4l2loopback)** | Loadable kernel modules on nodes; the `privileged` Pod Security Standard on the namespace; kernel headers and a toolchain for `method=build`, or a reachable registry and the KMM operator for `method=kmm`; kubelet's device-plugin socket at `/var/lib/kubelet/device-plugins`. · [how-to](../howto/kernel-modules-and-webcam.md) | Two halves, both required. Node prep loads `v4l2loopback` and re-loads it after every node reboot; the device plugin — Kasm's own, not a third-party one — advertises the resulting `/dev/video*` files as the extended resource `videoDevicePlugin.resourceName` (`kasm.com/video`), which kubelet then assigns one-per-pod. Set `nodePrep.modules.v4l2loopback.method=kmm` to build once per kernel into an OCI image instead of compiling on every node — the right choice at fleet scale, on Secure Boot nodes, and on node images with no compiler. Device count: `nodePrep.modules.v4l2loopback.videoDevices`. |
| **Session recording** | A Kasm license that includes session recording, and workspace pods able to reach the Kasm API Service to upload. | The agent adds a `podStartCommands` entry that launches the recorder inside the session pod, and a `podStopCommands` entry that holds the pod open until the upload finishes; `terminationGracePeriodSeconds` is set to `stopTimeout + 30` to cover it. Recordings buffer in a sized `emptyDir` at `/opt/kasm/recordings`, so an evicted or OOM-killed pod loses an in-flight recording. |
| **CUPS printing** | None. | Entirely in-pod: the agent adds a `podStartCommands` entry running `/etc/cups/start_cups.sh` when the session has the printer service on. The workspace image has to ship CUPS and `kasm_printer_service`, which the stock Kasm images do. |
| **Microphone (PulseAudio relay)** | None. | Same `podStartCommands` mechanism; the operator injects `PULSE_RUNTIME_PATH` and mounts the PulseAudio runtime at `/var/run/pulse`. Requires only that the workspace image carry PulseAudio and the microphone server binary. |
| **Startup and stop scripts (lifecycle commands)** | The operator's ServiceAccount needs `create` on `pods/exec` — the chart's RBAC already grants it. | `spec.podStartCommands` run as exec Jobs once the session pod passes its readiness probe; `spec.podStopCommands` run from a finalizer before termination, inside the grace period. This is the substrate the recorder, the printer, the squid adapter and the SSH-key `chmod` all ride on. |

### Storage

| Feature | Cluster prerequisites | How it works |
| ------- | --------------------- | ------------ |
| **Persistent user profiles** | A StorageClass with dynamic provisioning. `ReadWriteOnce` covers most provisioners (EBS, PD, Azure Disk, Longhorn, local-path); **shared** profiles need `ReadWriteMany` — NFS, EFS, Azure Files, CephFS. · [how-to](../howto/rwx-storage-for-profiles.md) | The profile itself is `spec.profiles` on the `KasmWorkspace` CR, driven by the Kasm manager, not by a chart value. When `persistent: true` the PVC name is stable and survives CR deletion; when false the PVC is garbage-collected with the CR. RWO pins the pod to the node holding the PV. The bundled NFS provisioner is a convenience for clusters with no RWX driver, not a production storage recommendation, and needs `nfs-server-provisioner.persistence.enabled=true` (plus a backing `storageClass` and `size`) or profiles are lost when its pod restarts. |
| **Cloud storage mappings (rclone / S3 / Drive)** | FUSE on every node that runs sessions (`/dev/fuse` present, `fuse` module loaded), outbound network access to the remote, and a publish namespace the operator can read Secrets from. · [how-to](../howto/cloud-storage-rclone-csi.md) | Both `csiRclone.enabled=true` and `agent.storageMappings.enabled=true` are required: the CSI driver alone mounts nothing, and the agent flag alone (`KASM_RCLONE_CSI_ENABLED`) points at a driver that isn't there. The operator derives a cluster-scoped StorageClass per unique rclone backend, keyed by a hash of the rclone INI, and keeps the credentials in a Secret — they never appear in the `KasmWorkspace` CR or the StorageClass. Scope the derived StorageClass and Secret names with `agent.storageMappings.installationID`. |
| **File mappings (injected config files)** | None. | `spec.fileMappings` becomes one ConfigMap per mapping, mounted with `subPath` per key so a single file drops into a directory without clobbering its neighbours; `defaultMode` carries the permission bits. The only limit is etcd's: a ConfigMap caps at 1 MiB. |
| **Host volume / bind mounts** | A namespace whose Pod Security Standard permits `hostPath` (`baseline` with exemptions, or `privileged`). · [how-to](../howto/privileged-workloads-and-policies.md) | `spec.volumeMappings` renders `hostPath` volumes of type `DirectoryOrCreate` and `spec.devices` renders `CharDevice`/`BlockDevice` mounts. The limitation is scheduling, not capability: Docker mounts any path on the one host it runs on, whereas an unpinned pod can land on a node where the path does not exist and fail its volume mount. Use `agent.workspacesNodeSelector` to pin sessions to the nodes that actually have the path. |

### Networking and access

| Feature | Cluster prerequisites | How it works |
| ------- | --------------------- | ------------ |
| **Network isolation (restrict-to-network)** | A CNI that **enforces** NetworkPolicy — Calico, Cilium, Antrea, Weave, Kube-router, GKE Dataplane V2, or AWS VPC CNI with Calico policy. Under Flannel or canal alone, every NetworkPolicy in the cluster is a no-op that silently succeeds. · [how-to](../howto/network-policy-enforcement.md) | The operator stamps a per-workspace policy by itself with no configuration: default-deny, then an ingress allow that admits the session proxy **by podSelector**, and egress limited to DNS, the manager namespace, and the internet minus the cloud metadata addresses. All session and manager traffic flows through the session proxy, so sessions work with **no namespace labels at all**, in every topology — including a manager in another cluster, where a namespaceSelector could never match. The `kasm.com/role=manager` namespaceSelector in the same rule covers only *direct* manager→workspace ingress, which does not normally occur: the label is **optional**. `networkPolicies.*` is the *agent's own* baseline and is a separate concern — leave it off in any namespace shared with the control plane. **Known gap:** Kubernetes NetworkPolicy filters L3/L4 but assigns no per-workspace egress IP; the Docker network plugin's per-container source IP would need Multus with a macvlan/ipvlan secondary interface, which the operator does not implement. The baseline is a namespace-scoped starting point; extend it with `networkPolicies.extraPolicies`. |
| **Egress gateways (per-session VPN)** | A namespace that permits `privileged` **and** host namespaces: the DaemonSet runs with `hostPID: true` and `hostNetwork: true`, so a blanket `disallow-host-namespaces` admission rule rejects it even in a privileged namespace. A runtime that honours chained CNI plugins. · [how-to](../howto/egress-installer-node-prerequisites.md) | This is the chained-CNI approach: the daemon installs a `kasm-egress-cni` shim into the node's CNI bin dir, patches every conflist in `egressInstaller.cniConfDirs` to chain it in, and on request `nsenter`s a session's netns to bring up an OpenVPN, WireGuard, or Ziti tunnel there — the workspace container itself needs no `NET_ADMIN`. Lifecycle, verified live on k3s: a **graceful** shutdown (uninstall, `helm upgrade` disabling it, rolling update, pod delete) restores every conflist from its `.kasm-egress.bak` and removes the shim, leaving the node as it was found. A **hard crash** skips that path — the chain stays patched until the replacement pod re-installs and re-verifies it. The residual risk is the no-daemon window: the shim hard-fails CNI ADD when it cannot reach the daemon's socket, and a failing chained plugin fails **every** pod sandbox on that node, not just Kasm's. Normally that window is a DaemonSet restart; a crash-loop or a pod lost without graceful termination extends it until a daemon returns or the conflist is restored by hand. The operator's older `spec.vpnSidecar` (a gluetun sidecar with `NET_ADMIN` in the session pod) remains available and needs no chart. Set `egressInstaller.distro` — or `egressInstaller.cniBinDir` outright — to the path your runtime really loads CNI plugins from. |
| **Web filtering (Squid / session proxy)** | Session pods must be able to reach the session-proxy Service; if `networkPolicies.enabled=true`, `networkPolicies.sessionProxy.*` has to permit it. · [how-to](../howto/network-policy-enforcement.md) | The agent substitutes the session-proxy Service address for the Docker agent's runtime IP discovery (`KASM_SESSION_PROXY_HOST`) and the per-session UUID for the upstream path, then starts the squid adapter via `podStartCommands`. Enforcement is application-layer and inside the session pod, so a root user in the workspace can interfere with it — the dependency doc flags moving this into an egress gateway as the intended direction. Nothing to set: the values are derived from `agent.publicHostname` and `agent.sessionProxy.*`. |
| **External access / ingress** | A Gateway API implementation, an ingress controller, or a cloud load balancer / MetalLB. Whatever fronts it must hold WebSockets open: idle timeout ≥ 3600s (`proxy-read-timeout` / `proxy-send-timeout` on ingress-nginx). DNS pointing at the external address. · [how-to](../howto/external-access-and-tls.md) | The two halves are exposed independently — the control plane is what users log in to, the agent's session proxy is what their browser streams from. Keep the control plane's `kasm-helm.proxyService.type` as `ClusterIP` when an ingress fronts it. **Real client IPs** need one more choice: `agent.sessionProxy.service.externalTrafficPolicy=Local` at L4 (traffic then only routes via nodes running a proxy pod), or `agent.sessionProxy.proxyProtocol.enabled=true` with `agent.sessionProxy.proxyProtocol.trustedCIDRs` at L7 — and in that case the fronting proxy **must** actually send PROXY protocol, or every connection breaks. `agent.gatewayRoute` is the operator-managed Gateway API TLS passthrough and the preferred route; `agent.route` is the OpenShift path; `agent.httpRoute` additionally needs `agent.httpRoute.parentRefs` and `agent.httpRoute.hostnames`. TLS passthrough via `agent.gatewayRoute` verified live on Traefik 3.7 / Gateway API 1.5.1: the operator-managed TLSRoute attached to a `Passthrough` listener sharing port 443 with the terminated listener, and the client received the session proxy's own certificate end-to-end. |
| **RDP gateway** | Outbound TCP 3389 from the gateway pods to the target hosts, and DNS/routing to reach them. | Both gateways ship as ordinary Deployments and Services in the control-plane chart and are on out of the box. **RDP targets are external** — Windows or Linux hosts outside the cluster; the gateway brokers to them, it does not host them. The Go `rdp-https-gateway` also needs its Service reachable by clients if you expose it separately. Both gateway components default to `true`; `kasm-helm.directRdpService.*` is optional and only for native-client access. |

### GPU

| Feature | Cluster prerequisites | How it works |
| ------- | --------------------- | ------------ |
| **GPU acceleration (CUDA / compute)** | GPU hardware, and nodes labelled (and usually tainted) for GPU workloads. The GPU Operator installs the driver, container toolkit, device plugin and RuntimeClass itself; if you already run NVIDIA's device plugin, leave `gpuOperator.enabled=false` and set only `agent.gpu.enabled=true`. · [how-to](../howto/gpu-nodes.md) | Both values, always: the operator advertises `nvidia.com/gpu` that nothing requests, and `agent.gpu.enabled` (which sets `KASM_GPU_OPERATOR_ENABLED`) is what makes the agent put `nvidia.com/gpu: N` in the workspace's resource limits. The GPU Operator is cluster-scoped — install it once per cluster, not once per agent release. **Difference from Docker:** kubelet's Device Plugin API owns allocation, which is more robust than the Docker agent's own GPU bookkeeping but removes the Kasm-level GPU metadata. |
| **GPU graphics acceleration (EGL / DRI)** | GPU drivers pre-installed in the **node image**, with `/dev/dri/card0` and `/dev/dri/renderD128` present; GPU nodes labelled so sessions can be targeted at them. · [how-to](../howto/gpu-nodes.md) | No device plugin is strictly required for DRI alone — the operator adds `spec.devices` `hostPath` `CharDevice` mounts for the DRI nodes when the workspace image carries the `com.kasmweb.gpu_acceleration_egl=nvidia` label and GPU support is on. Preparing the node image is genuinely outside any chart here. **Difference from Docker:** the operator assumes the first available DRI device; topology-aware multi-GPU assignment is not implemented. `agent.gpu.enabled=true` gates the DRI device mounts alongside CUDA. |

### Security and policy

| Feature | Cluster prerequisites | How it works |
| ------- | --------------------- | ------------ |
| **SSH key injection** | None. | Rides the file-mapping path: the agent writes `id_rsa` and `id_rsa.pub` into a ConfigMap mounted at `/home/kasm-user/.ssh/`, then a `podStartCommands` entry `chown`s them to `1000:0` and `chmod 400`s the private key. |
| **Kernel module management (WireGuard)** | Only relevant on **kernels older than 5.6**; from 5.6 WireGuard is in-tree and nothing is needed. Where it is needed: `privileged` PSS, `/lib/modules` and `/usr/src` on the node, kernel headers, and network access to fetch the source. · [how-to](../howto/kernel-modules-and-webcam.md) | The installer detects an in-tree WireGuard (`wg_` in `/proc/kallsyms`) and exits early rather than building, so leaving this on across a mixed fleet is safe. Most managed Kubernetes runs ≥ 5.6, which makes this a no-op for the majority of clusters. Same machinery as the `v4l2loopback` path, including reboot re-application. |
| **TLS / trusted CA** | cert-manager, if you use the cert-manager paths on either side. Otherwise a TLS Secret you create yourself. · [how-to](../howto/external-access-and-tls.md) | Each half terminates its own TLS — the control plane at its ingress (`kasm-helm.certificate.secretName`, or `kasm-helm.certificate.certManager.enabled=true` with `kasm-helm.certificate.certManager.issuerName`), the agent at the session proxy (`agent.sessionProxy.certificate.enabled=true` with `agent.sessionProxy.certificate.issuerRef`, or `agent.sessionProxy.certSecretName`). Internal CAs go in with `kasm-helm.trustedCaBundle.enabled=true` and `kasm-helm.trustedCaBundle.caCerts`. CA certificates **inside sessions** are a different mechanism: they go in as file mappings under `/usr/local/share/ca-certificates/`, with a `podStartCommands` entry running `update-ca-certificates`. |
| **Private image registries** | A `kubernetes.io/dockerconfigjson` Secret in the right namespace. ECR tokens expire every 12h — keep them fresh with the ECR credential helper or external-secrets; on GCP prefer Workload Identity. · [how-to](../howto/private-registries-and-image-pulling.md) | The two settings are genuinely different: `agent.workspaceImagePullSecrets` is what the agent injects into the session pods it launches, `agent.imagePullSecrets` is what pulls the agent and proxy images themselves. Pull secrets also propagate to the image-puller DaemonSet, and `agent.imagePuller.images[].imagePullSecrets` can override per image. Every other chart carries its own `imagePullSecrets` list for its own images, and the control plane has `kasm-helm.imagePullSecrets.enabled=true`. |
| **Multi-tenancy / namespace isolation** | NetworkPolicy enforcement, Pod Security Standards on session namespaces, ResourceQuota and LimitRange to stop one tenant exhausting a node. All are cluster policy decisions no chart can make. · [how-to](../howto/network-policy-enforcement.md) · [how-to](../howto/privileged-workloads-and-policies.md) | What ships is real but basic: the operator's default per-workspace NetworkPolicy isolates each session pod from every other pod in its namespace, `automountServiceAccountToken: false` denies sessions any API access, and `fsGroup: 1000` normalises file ownership. Strong tenant isolation — a namespace per user or per group — needs provisioning automation on top, and the same namespace that permits `privileged` for `nodePrep` or `egressInstaller` weakens the PSS story for everything else in it. Separate releases per tenant — the two-namespace topology in [architecture.md](../architecture.md#deployment-topologies) is the recommended baseline. |
| **Secure Boot (signed kernel modules)** | MOK keys **enrolled in each node's UEFI** — a one-time manual step per node, or baked into the node image. The key pair stored as a Secret in the namespace where the installer runs. · [how-to](../howto/secure-boot.md) | Only matters where Secure Boot is on, which is mostly bare metal and private cloud; EKS, GKE and AKS do not enable it by default, and with Secure Boot off this can be ignored entirely. The build path (`nodePrep.secureBoot.existingMokSecret`) signs the freshly built `.ko` before `insmod`; the KMM path (`nodePrep.modules.v4l2loopback.kmm.sign.enabled=true` with `kmm.sign.keySecret` and `kmm.sign.certSecret`) signs as part of producing the per-kernel image, which is the cleaner option if you are already choosing between them. |

### Operations and platform

| Feature | Cluster prerequisites | How it works |
| ------- | --------------------- | ------------ |
| **Image pre-pulling** | The container runtime socket reachable from DaemonSet pods (`/run/containerd/containerd.sock`, or the CRI-O equivalent), and registry access or a local mirror from every node. · [how-to](../howto/private-registries-and-image-pulling.md) | Two paths coexist. The operator creates a `KasmImagePuller` from the manager's own image list without being asked; `agent.imagePuller.*` renders an explicit one for images you want staged regardless. Either way it is a DaemonSet using `crictl` against the runtime socket, which is broad node access — worth an explicit decision on clusters with tight node-level policy. `agent.imageAvailabilityPolicy` (`all` or `any`) decides when an image counts as available. |
| **Node targeting / pool assignment** | A consistent node-labelling strategy (`kasm-gpu=true`, `kasm-webcam=true`, and so on), and GPU node taints tolerated where relevant. · [how-to](../howto/gpu-nodes.md) | Per-workspace targeting needs no chart value at all: the agent translates the manager's `include_labels` into `spec.nodeSelector` on the `KasmWorkspace`. `agent.workspacesNodeSelector` sets the fleet-wide default (`KASM_NODE_SELECTOR`), which also pins the agent-managed module installer and device plugin. `agent.nodeSelector` targets the agent's own pods, not the sessions. |
| **Autoscaling** | Cluster Autoscaler or Karpenter, configured against node groups that match workspace pod requests — including separate GPU node groups if GPU sessions autoscale. | Node-level autoscaling is a cluster concern and works normally. What is missing is the Kasm-specific half: session-density-aware scaling is **not** wired to HPA or KEDA. The operator does reconcile `WarmPool`/`WarmPoolInstance` resources (a pre-warmed pod set with `spec.replicas` and a `spec.runtimeImage`), which cuts cold-start latency, but that is pre-warming, not demand-driven scaling. `KasmPool`/`KasmVMProvider` still manage Kasm-level pools and VM providers from the manager side and are not part of these charts. `operator.enabled=true` is what installs the `warmpools.pools.kasm.ai` and `warmpoolinstances.pools.kasm.ai` CRDs and the controller that reconciles them; no chart value creates a WarmPool. |
| **Telemetry** | An OTLP-speaking backend and/or a ClickHouse instance. If `networkPolicies.enabled=true`, open the path with `networkPolicies.otelBackend.cidr`. · [how-to](../howto/network-policy-enforcement.md) | The collector receives traces, metrics and logs from the operator, the agent and the sessions and fans them out; `otelCollector.exporters.debug.enabled=true` is the quickest way to confirm data is arriving before pointing it anywhere real. Kubernetes events come in with `otelCollector.receivers.k8sEvents.enabled=true`. |

## Source

Sections 1 to 3 are the configuration surface of a live **Kasm Workspaces 1.19.0** control plane,
read from its own schema: the `images` table (workspace settings), `group_settings` (group and
session settings), and `settings` (global settings, keyed by category and name). What each one
becomes on Kubernetes is grounded in the agent operator's custom resource definitions —
`KasmWorkspace` and `Agent` — read from the API server of the cluster this repository is developed
against. Where a setting maps to a CR field, that field is named; where it maps to nothing, the row
says so.

The infrastructure notes in section 4, their cluster prerequisites and the how-to guides they link
to began as Kasm's internal *Kasm Feature to Kubernetes Dependency Matrix*
(`k8s-feature-dependencies.md`); it is credited here as implementation notes for that layer, not as
the feature list. The chart and value mappings throughout are this repository's, verified against
each chart's `values.yaml`.

Every limitation stated here was observed on a running session in the lab cluster, not inferred
from the two systems' documentation. The exceptions, named where they occur, are
`gpu_video_encoding` (no GPU nodes in this lab) and the settings that never reach the cluster at
all.
