Bringing OpenTelemetry to the Kasm Helm Chart

The feature/DEV-31 branch gave the Docker installer a full observability stack: an OpenTelemetry Collector, a bundled ClickHouse store, distributed tracing through nginx, and browser-side telemetry. This is the plan to bring the same capability to Kubernetes customers through the kasm-helm chart.

1Executive summary

Kasm's Docker installs now ship telemetry by default: every service exports logs, traces and metrics over OTLP to a local OpenTelemetry Collector, which writes them to a bundled ClickHouse database that backs the reporting UI. nginx participates as the root of each trace, and the browser contributes real user timings. None of that exists in the Helm chart today.

Feature parity

Kubernetes customers get the same telemetry, reporting and retention behaviour as Docker customers, configured the Kubernetes way rather than by porting bind mounts.

On by default

ClickHouse and the Collector are part of Kasm, not an add-on. Customers opt out or point at their own infrastructure; they don't opt in.

Standards-first

Plain OTLP and standard OTEL_* environment variables throughout, so customers can drop in their own collector or observability vendor.

Thin configuration

A small set of Helm values for endpoints, credentials and retention. Anything deeper is a Collector ConfigMap the customer can replace outright.

Scope at a glance: eleven new chart templates, roughly fifteen touched, two templates deleted, a new observability.* values tree, nine new unit-test suites, three new end-to-end scenarios, and one new customer-facing documentation page. The backend prerequisite this depended on has already landed (see §11).

2Design decisions

These were the open questions; all are now settled and drive the rest of the plan.

QuestionDecisionWhy
How do logs leave the pods? OTLP to the Collector is the default and recommended path. File-based JSON remains available via a shared volume plus a sidecar. Printing collected logs to a pod's stdout is supported but not recommended. As OTel-native as possible, while keeping today's "scrape the pod logs" workflow available for customers who depend on it.
How are nginx logs collected? A Collector DaemonSet on every node reads the container runtime's log files from /var/log/pods, scoped to this release's proxy pods only. The standard Kubernetes centralized-logging pattern. Nothing is added to the proxy pod. Because the file-path glob already selects our own pods, pod metadata comes from the path and the chart needs no ServiceAccount and no cluster permissions.
Is ClickHouse bundled? Yes, deployed and enabled by default; disable or externalise through values. ClickHouse is part of Kasm, the same way the bundled Postgres is.
Multi-zone deployments? Two tiers: a lightweight forwarder Collector per zone, and a single cluster-wide gateway Collector that samples traces and writes to ClickHouse. Mirrors how the chart already renders per-zone workloads, and how the Docker install already splits its own Collectors. A single tier per zone cannot sample traces correctly — see §5.
ClickHouse TLS? Follow the bundled Postgres shape: mount the shared Kasm certificate and enable the TLS ports. Consistency with an existing, understood pattern in the chart. Needs one small backend change first — see §11.
Collector config: values or ConfigMap? A ConfigMap per tier, each with its own existingConfigMap escape hatch, plus worked examples. Only endpoints, credentials and retention numbers stay in values. Dozens of values that all collapse into one YAML file is worse than letting customers copy and modify that file directly.

Fixed technical facts

  • Collector ports: 4318 OTLP/HTTP for local services, 4317 OTLP/gRPC with bearer auth for out-of-cluster senders, 4316 OTLP/gRPC unauthenticated for nginx (its module cannot present a bearer token), 13133 health, 8888 Collector self-metrics.
  • ClickHouse: 8123 HTTP, 9000 native, 8443 HTTPS, 9440 native TLS. Database and user kasm_otel.
  • Retention defaults: application logs 30 days, audit logs 365 days, traces 7 days, metrics 90 days. Audit classification happens at insert time inside ClickHouse.
  • Trace sampling: tail-based; all errors and all requests slower than one second are always kept, plus 10 % of everything else.

4Logging: going OTel-native

The backend refactor replaced Kasm's hand-rolled logging configuration with the shared kasm_telemetry library. Console output is now always human-readable text; the machine-readable copy goes out over OTLP, and optionally to a JSON file. There is deliberately no "JSON to console" mode.

That gives customers three ways to get logs into their own tooling:

PathHow it worksGuidance
1. OTLP to the Collector Services export directly to the Collector Service. From there, ClickHouse, a forwarding endpoint of the customer's choosing, or both. Default & recommended
2. JSON file + sidecar Services write JSON log files to a shared emptyDir; a Collector sidecar tails them. Supported For customers who want file-shaped JSON.
3. Collector debug output The Collector prints what it received to its own stdout, where an existing cluster log scraper can pick it up from a single pod. Not recommended Closest to today's behaviour; documented as a fallback only.
Customer-visible change

logFormat: json narrows in meaning. It continues to control the nginx access-log format and the Postgres JSON log, but it no longer affects API or Manager console output, which is always text. Customers who rely on scraping JSON from API/Manager pod logs need to move to path 1 (recommended) or path 2. This needs to be called out in the release notes.

Two consequences inside the chart:

  • The api-app-configmap and manager-app-configmap templates — roughly 570 lines of logging configuration — are no longer read by the application and get deleted. Their remaining keys duplicate the container image's own defaults and are already overridden by environment variables.
  • File logging must be explicitly disabled unless path 2 is in use, because the chart runs containers with a read-only root filesystem and no log volume.

5Collector topology

Telemetry moves through two Collector tiers. A forwarder Deployment in each zone receives everything the Kasm services and nginx emit, batches it, and passes it on. A single gateway Deployment then makes the trace-sampling decision and is the only writer to ClickHouse. This is not an extra layer for its own sake — it is the same split the Docker install already ships, and the reason is in the callout below.

Why sampling must live in exactly one place

Trace sampling is a decision about a whole trace: keep it if any span errored, or if the request was slow, otherwise keep a set percentage. To make that call, one process has to see every span in the trace.

A single Collector tier cannot guarantee that. A request that crosses zones sends its spans to two different zone Collectors, and even inside one zone the deployment presets run two replicas at medium and large, with a Service spreading spans across them. Each instance would then vote on a fragment of the trace, and traces would arrive with spans missing while the sampling percentage quietly stopped meaning what it says. Nothing errors; the data is simply wrong.

Hence the split. Forwarders hold no state and scale freely; the gateway runs as a single instance and owns sampling alone. Concentrating the ClickHouse writes there is a bonus — ClickHouse degrades under many small concurrent inserts, and one writer keeps batches consolidated.

nginx logs need one more piece. Docker runs one Collector per host and bind-mounts the nginx log directory into it. The Kubernetes equivalent of “one collector per node reading local log files” is a DaemonSet that mounts /var/log/pods. nginx writes to stdout and stderr, the container runtime persists that to the node's filesystem, and the node-local Collector tails it — the standard centralized-logging pattern, and nothing at all is added to the proxy pod.

Crucially, the chart knows its own release name and namespace when it renders, so the DaemonSet reads only /var/log/pods/<namespace>_<release>-proxy-*/*/*.log. That is narrower than the usual “collect everything, then filter” recipe and it buys three things: it never reads another workload's logs, it does far less file I/O per node, and pod metadata can be derived from the file path — so no ServiceAccount and no RBAC are needed at all. The chart creates zero RBAC objects today, and this keeps it that way.

The container runtime records which stream each line came from, so one receiver handles both: the JSON access log from stdout and nginx's plain-text error log from stderr are routed to different parsers. kubectl logs behaviour is unchanged, and there is one collection path instead of two. Log-file read offsets are checkpointed on the node, so restarting the DaemonSet neither loses nor repeats lines.

The Pod Security trade-off — and why a sidecar still exists

hostPath volumes are forbidden by both the baseline and restricted Pod Security Standards, and reading /var/log/pods requires running as root, which restricted also forbids. This chart advertises — and end-to-end tests — restricted-namespace support.

So the DaemonSet cannot run in a namespace that enforces either profile. For those customers the original sidecar mechanism is retained as a documented, default-off alternative: a shared volume and a Collector sidecar in the proxy pod. It is the only way to collect nginx logs under restricted pod security, and it costs almost nothing to keep because the same sidecar helper already serves optional file-based logging. Enabling both mechanisms at once is a configuration error and fails the install.

nginx traces are unaffected in every case — the module talks to the Collector over the network and needs neither mechanism.

6Two things that break existing behaviour

Both were found while reading the two codebases side by side. Neither is optional.

Blocker 1 — the chart overwrites the file that loads the nginx OTel module

The Kasm nginx image ships the OpenTelemetry module and injects a load_module directive as the first line of its nginx.conf. The chart mounts its own nginx.conf over that path, so the module would never load — and every otel_* directive would become a fatal "unknown directive" error that stops nginx from starting at all.

Fix: the chart must emit the load_module line itself, as the first line of the config it renders. The module is inert when tracing is switched off, so this is safe unconditionally. The same applies to the Guac and RDP gateway nginx sidecars.

Blocker 2 — the chart's JSON logging configuration is now dead code

The API server no longer loads the logging section of its application config file, so the two large ConfigMaps the chart maintains for JSON logging are mounted and ignored. The existing end-to-end test asserting JSON output from every pod will fail for API and Manager.

Fix: delete both ConfigMaps, adopt the logging paths in §4, and re-scope that test to cover nginx and Postgres stdout plus the new sidecar path.

7Configuration surface

Deliberately small. A value earns its place only if it is an endpoint, a credential, or a number the chart needs in more than one place — retention days, for example, are written both into the ClickHouse schema and into the Collector's exporters. Everything else lives in the Collector ConfigMap, which customers can replace in full. 

observability:
  enabled: true                    # master switch for the whole stack

  collector:
    externalEndpoint: ""           # use an existing Collector; deploys neither tier
    image: {...}                   # both tiers run the same image

    forwarder:                     # one per zone — what services export to
      existingConfigMap: ""        # bring your own forwarder config
      replicas: 0                  # 0 = size preset
      resources: {}
      externalService:             # expose :4317 to out-of-cluster agents/zones
        {enabled: false, type: LoadBalancer, annotations: {}}
    gateway:                       # one per cluster — samples and writes
      existingConfigMap: ""        # bring your own gateway config
      replicas: 0                  # 0 = size preset, which is 1 at every size
      resources: {}

    tailSamplePercentage: 10       # pipeline behaviour: applied at the gateway
    forward:                       # ship a copy to any OTLP backend, post-sampling
      endpoint: ""
      token: ""
      existingSecret: {name: "", key: ""}

  fileLogs:                        # logging path 2 — off by default
    enabled: false
    sizeLimit: 512Mi
    components: [api, manager, guac]

  hostLogs:                        # DaemonSet reading /var/log/pods (default path)
    enabled: true
    persistOffsets: true           # checkpoint read offsets on the node
    extraSelectors: []             # e.g. kasm-db-* to also collect the database
    tolerations: []

  nginxLogs:                       # sidecar alternative for restricted-PSS namespaces
    enabled: false                 # mutually exclusive with hostLogs
    sizeLimit: 512Mi

  clickhouse:
    enabled: true                  # false = no telemetry store at all
    standalone: false              # true = use an external ClickHouse
    nativeEndpoint: ""             # external: Collector write path
    httpEndpoint: ""               # external: Kasm reporting read path
    database: kasm_otel
    username: kasm_otel
    existingSecret: {name: "", key: ""}
    tls: true
    image: {...}
    resources: {}
    storage:
      storageClassName: ""
      pvcSize: 20
      retentionPolicy: {whenDeleted: Retain, whenScaled: Retain}
    retention:
      {logsDays: 30, auditLogsDays: 365, tracesDays: 7, metricsDays: 90}

  browser:
    enabled: true                  # real-user telemetry from the Kasm web UI
The escape hatch

Each tier has its own existingConfigMap, so a customer can take over the gateway's config — where sampling and storage live — without also having to hand-maintain the forwarder's, or vice versa. We ship worked examples to start from — a documented skeleton, a Splunk HEC variant (replacing the migration script the Docker installer uses), and a debug-output variant for logging path 3. The chart already uses this pattern for the RDP gateway's rdpproxy.ini and for trusted CA bundles, so it is familiar territory.

The chart will refuse to render, or warn, on the same invalid combinations the installer rejects: external ClickHouse endpoints must be supplied in pairs; an external store cannot be combined with "no store"; a customer-supplied Collector config makes the config-shaping values inert.

End-to-end tests (real cluster)

  • Default install — Collector and ClickHouse healthy; after driving a login, telemetry rows for API, Manager, proxy and Guac are actually present in ClickHouse.
  • Telemetry disabled — no observability objects, every pod healthy, browser telemetry reports itself as off.
  • File-based logging — JSON present in the shared volume and the same records arriving in ClickHouse through the sidecar.
  • Restricted pod security — the chart installs and runs in a restricted namespace with the DaemonSet disabled and the sidecar path enabled, keeping the chart's advertised support honest.
  • Existing JSON logging test — re-scoped per §4.

Both new workloads must also satisfy the chart's existing Pod Security Standards and policy checks, including required probes and resource limits.

11Open risks & dependencies

Backend prerequisite — now resolved

Kasm's reporting code creates its ClickHouse client without specifying how to verify the server's TLS certificate, so it falls back to full verification against the system trust store. Kasm presents a self-signed certificate on that interface — both in this chart and on the dedicated ClickHouse role that already ships in the Docker installer. Report queries over HTTPS will therefore fail certificate verification.

Done. The reporting client can now be told which certificate to trust (preferred, since verification then genuinely succeeds) or told to skip verification. Landed on the backend, together with a second change making the ClickHouse database name configurable so Kasm can share a multi-tenant ClickHouse — the reporting queries no longer hard-code it.

One follow-up remains, and it is a Docker-side gap rather than a Helm one: the installer does not yet set either variable automatically for the dedicated ClickHouse role, so that topology still needs them supplied by hand.

Other items to keep an eye on

  • Storage sizing. ClickHouse adds a PersistentVolumeClaim, defaulting to 20 GiB. We need sizing guidance in the documentation tied to the retention defaults, and customers on clusters without a default storage class need a clear message.
  • nginx connection metrics are not collected on the default path. A node-level DaemonSet cannot reach a pod's loopback interface, and scraping the proxy Service round-robins across replicas, which corrupts cumulative counters. Request rate, latency and status-code distribution all still come from the access logs and traces; the one signal lost is the count of currently-active connections. Two ways to recover it later: pod discovery in the DaemonSet, which would add cluster permissions the chart does not currently need, or the sidecar path, which already collects them.
  • Restricted pod security needs a different setting. Customers enforcing the baseline or restricted Pod Security Standards must disable the DaemonSet and enable the sidecar instead. This is documented, tested, and called out in the release notes, but it is a default that does not fit every cluster — worth saying out loud to customers rather than letting them discover it through a failed install.
  • Resource footprint. Three new workloads — a forwarder Collector per zone, one gateway Collector, and ClickHouse — plus a DaemonSet pod on every node and, optionally, a sidecar per proxy pod. These need sensible requests and limits per deployment size, and a mention in the upgrade notes so existing clusters are not surprised.
  • Splunk continuity. Customers upgrading from 1.19 or earlier whose Splunk settings lived in the Kasm database must move them into a Collector config. This needs a prominent release note, not just a documentation page.
  • Trace sampling expectations. Only 10 % of healthy traffic is retained by default. Errors and slow requests are always kept, but this should be stated plainly so nobody concludes that traces are missing.
  • The gateway is a single instance, and scaling it needs real work. Correct sampling requires one process to see a whole trace, so the gateway does not scale horizontally the way the forwarders do. Very large deployments will eventually want trace-ID-aware load balancing in front of a sampling tier; until then the gateway's ceiling is vertical. Worth stating in the sizing guidance so nobody raises the replica count expecting more throughput and silently loses spans.
  • Documentation reach. Beyond the chart's own new page, the public observability documentation needs a Kubernetes column throughout; that work is already tracked on the backend side.
