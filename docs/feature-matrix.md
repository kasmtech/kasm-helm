# Kasm workspace features → what to install

The rows below are the actual configuration surface of a **Kasm Workspaces 1.19.0** control plane —
every column of a Workspace (the `images` table), every group and session toggle
(`group_settings`), and every global setting (`settings`) — each mapped to what provides it when
the sessions run as pods instead of as Docker containers. Four answers recur. Some settings are
pure control-plane state and behave identically whatever runs the container. Some become a field on
the `KasmWorkspace` custom resource, which the agent operator reconciles into a Deployment, a
Service, and whatever volumes, policies and lifecycle hooks the field asks for. Some need a chart
in this repository switched on, or something to exist in the cluster first. And a few have no
Kubernetes equivalent at all, which this page says plainly rather than quietly. Every value cited
below exists in one of this repo's `values.yaml` files; every chart name links to its own README,
which is the full reference.
Running on a managed service? [Managed Kubernetes providers: what changes](howto/managed-kubernetes-providers.md)
collects what EKS, AKS, GKE and OpenShift decide for you — node OS, load balancer, security
baseline — and which rows below drop out on serverless node pools.

**Status vocabulary**

| Status | Meaning |
| ------ | ------- |
| `Works by default` | The agent or operator does it. Nothing to enable in the charts. |
| `Enable in chart` | A value in this repo flips it on. |
| `Needs cluster infra` | The charts help, but something has to exist in the cluster first. |
| `Partial` | Works, with a stated limitation relative to the Docker agent. |
| `Not on Kubernetes yet` | No Kubernetes equivalent exists, or the operator does not implement one. |

In **Values to set** — and in the **Provided by** column of sections 1 to 3 — stacked values are
all required; a line reading *or* separates alternatives. One value per line; qualifiers belong in
**Notes**.

Values are written as they are set on the **`kasm-agent`** umbrella (so `agent.*` is the
`kasm-agent-instance` subchart, `nodePrep.*` is `kasm-node-prep`, and so on). Under
[kasm-platform](../charts/kasm-platform/README.md), prefix them with `kasm-agent.` —
`kasm-agent.nodePrep.enabled`. Control-plane values are shown with their `kasm-helm.` prefix as
they are set from `kasm-platform`; drop it when installing
[kasm-helm](../charts/kasm-helm/README.md) directly.

The four sections follow the shape of the configuration itself:
[**1. Workspace (image) settings**](#1-workspace-image-settings) ·
[**2. Group & session settings**](#2-group--session-settings) ·
[**3. Global settings**](#3-global-settings) ·
[**4. Cluster infrastructure**](#4-cluster-infrastructure), the numbered rows the how-to guides
reference and everything in sections 1 to 3 ultimately points into.

## 1. Workspace (image) settings

Every column of the `images` table — the Workspace form in the admin UI — and what carries it when
the session is a pod. The `KasmWorkspace` custom resource is the contract: the agent turns a launch
request into one CR, and the operator reconciles that CR into the running session. A setting with
no field on the CR does not reach the cluster at all, which is not the same as being broken —
most of the catalogue is control-plane state that was never the runtime's business.

| Setting(s) | On Kubernetes this becomes | Status | Provided by | Notes |
| ---------- | -------------------------- | ------ | ----------- | ----- |
| **Catalog & presentation** — `name`, `friendly_name`, `description`, `image_src`, `categories`, `hidden`, `enabled`, `available`, `notes`, `hash`, `uncompressed_size_bytes`, `session_banner_id`, `session_banner_force_disabled`, `link_url`, `image_type`, `server_id`, `server_pool_id`, `restrict_to_server` | Nothing. Control-plane state that never leaves the manager. | `Works by default` | manager / UI<br>optional preseed:<br>`kasm-helm.kasmConfig.generatePreseed=true`<br>`kasm-helm.kasmConfig.config` | The catalogue lives in the control-plane database; the cluster only ever sees the one workspace being launched. `image_type` is the fork in the road — only **Container** workspaces become pods. **Server** and **Server Pool** target a VM or physical host brokered over RDP/SSH/VNC ([row 21](#networking--access)), and **Link** is a bookmark; none of the three involve the agent, which is why `server_id`, `server_pool_id` and `restrict_to_server` have no Kubernetes counterpart. `hash` and `uncompressed_size_bytes` describe the image, not the pod; `available` is the manager's view of whether the image is staged, which the image puller feeds ([row 15](#operations--platform)). `kasm-helm.kasmConfig.config` can seed the whole catalogue at database initialisation — fresh installs only. (`image_id`, `created_at` and `updated_at` are database bookkeeping and appear nowhere else.) |
| **Compute sizing** — `cores`, `memory_bytes`, `x_res`/`y_res` | `spec.resources` on the `KasmWorkspace` | `Works by default` | operator-native | The agent fills the CR's resource requirements from the workspace's `cores` and `memory_bytes`, and the operator passes them to the Deployment. `x_res`/`y_res` are display geometry inside the session, not a Kubernetes resource — they arrive with the desktop environment variables the operator injects. Size memory honestly: the per-session `/dev/shm` `emptyDir` is memory-backed, so it counts against the pod's memory limit and toward node pressure ([node best practices](../charts/kasm-agent/README.md#workspace-node-best-practices)). |
| **CPU allocation method** — `cpu_allocation_method` (Inherit / Shares / Quotas), global `images/default_cpu_allocation_method` | `cores` → `spec.resources` CPU. **Shares** (and *Inherit* under the default) sets a CPU **request only** — burstable, no ceiling (the Docker `cpu-shares` analogue). **Quotas** sets the CPU request **and an equal CPU limit** — a hard cap (the `cpu-quota` analogue). Memory (`memory_bytes`) always sets both request and limit. | `Partial` | operator-native (`spec.resources`) | Observed on a live session: Shares/Inherit → `requests.cpu=1`, no `limits.cpu`; Quotas → `requests.cpu=1` and `limits.cpu=1`; memory `1536Mi` request+limit in all cases. There is no oversubscription mode beyond those two — Kubernetes has no share weighting. The chart's node guidance arrives at the same place from the node side: leaving a workspace without a CPU limit is what reproduces Kasm's default Shares behaviour, "only throttled if there is CPU contention" ([node best practices](../charts/kasm-agent/README.md#workspace-node-best-practices)). Re-verified on a 1.1200.0-develop control plane with the same agent build: Quotas → `requests.cpu=2` and `limits.cpu=2` — the mapping is agent-side and unchanged across manager versions. |
| **Image source & registry credentials** — `docker_registry`, `docker_user`, `docker_token` | `docker_registry` is honored as the image reference **only when the image name itself carries the registry host** (e.g. `registry.gitlab.com/...`). Per-image `docker_user`/`docker_token` **are** materialized by the agent into a per-registry `kubernetes.io/dockerconfigjson` Secret (`kasm-registry-<registry-host>`, scheme and `/v1/` stripped) and updated in place when the credentials change. Chart-level `agent.workspaceImagePullSecrets` (every workspace pod) and `agent.imagePuller.images[].imagePullSecrets` (pre-pulls) still apply for fleet-wide registries. | `Partial` | operator-native (per-image Secret)<br>`agent.workspaceImagePullSecrets` | Verified on live sessions against a 1.1200.0-develop control plane: a `registry.gitlab.com` image with a valid deploy token launched with Secret `kasm-registry-registry-gitlab-com` generated and referenced from `spec.imagePullSecrets`; flipping the user updated that Secret in place, and restoring it re-synced it. Residual gaps: (1) for a Docker-Hub-style image name (`kasmweb/doom:develop`) with `docker_registry: https://kcr.kasmweb.com/v1/`, the Kubernetes agent pulls from Docker Hub and creates `kasm-registry-kcr-kasmweb-com` **without attaching it** — the `docker_registry` setting is not applied to the image reference, so a registry-scoped private image would fail to pull; (2) Secrets are not garbage-collected — an old-name `kasm-registry-https-…` Secret from before the naming fix stays behind. Test note: writing `docker_token` by direct SQL stores plaintext in an encrypted column and makes `request_kasm` return HTTP 500 — a test artifact, not a product path; set credentials through the UI/API. See row 23 and the [private registries how-to](howto/private-registries-and-image-pulling.md). |
| **Run / exec / launch configuration** — `run_config`, `exec_config`, `launch_config`, group `run_config` | The subset of Docker run options that has a `KasmWorkspace` field | `Partial` | operator-native | `run_config` is a Docker `create`/`run` payload and only part of it survives translation. Honoured, because the CR has a field for each: `shmSize` (`shm_size`), `devices`, `securityContext` (`cap_add`, `privileged`), `command` and `args`, `env`, `annotations` and `labels`, `stopTimeoutSeconds`, `healthCheck` (overrides the default TCP probes), `imageMounts`, `initContainer`, and `podOverrides` as the escape hatch for anything else expressible as a pod-spec patch. `exec_config` becomes `podStartCommands`/`podStopCommands` ([row 19](#sessions--media)). Docker-only keys — `network_mode`, `ulimits`, `hostname`, `dns`, restart policy, `pid_mode` and the rest — have no equivalent and have no effect: they are host-runtime concerns the pod sandbox owns. `imageMounts` needs the ImageVolume feature (Kubernetes 1.35+), with no host-unpack fallback. |
| **Persistent profiles** — `persistent_profile_path`, `enforce_workspace_persistence`, group `allow_persistent_profile` | `spec.profiles` — a PVC mounted at the profile path | `Needs cluster infra` | a StorageClass with dynamic provisioning<br>or<br>`nfs-server-provisioner.enabled=true`<br>`nfs-server-provisioner.persistence.enabled=true` | The CR field carries `mountPath`, `capacity`, `storageClass` and `persistent`; when `persistent` is true the PVC outlives the CR. Which access mode you need, why shared profiles force `ReadWriteMany`, and the in-cluster NFS fallback are [row 2](#storage) · [how-to](howto/rwx-storage-for-profiles.md). |
| **Volume mappings** — `volume_mappings`, group `volume_mapping` | `spec.volumeMappings` — `hostPath` volumes of type `DirectoryOrCreate` | `Partial` | `agent.workspacesNodeSelector` | The mapping itself works; scheduling is the limitation. Docker mounts a path on the one host it runs on, whereas an unpinned pod can land on a node where the path does not exist and fail its mount. Node targeting is the fix — [row 17](#storage) · [how-to](howto/privileged-workloads-and-policies.md). |
| **User storage mappings** — group `allow_user_storage_mapping`, `max_user_storage_mappings`, `read_only_user_storage_mapping` | `spec.storageMappings` — an rclone CSI volume per remote | `Needs cluster infra` | `csiRclone.enabled=true`<br>`agent.storageMappings.enabled=true` | Both values, always: the driver alone mounts nothing and the agent flag alone points at a driver that is not there. Credentials stay in a Secret and never appear in the CR. [row 3](#storage) · [how-to](howto/cloud-storage-rclone-csi.md). |
| **File mappings** — the workspace and group file-mapping tables (no `images` column of their own) | `spec.fileMappings` — one ConfigMap per mapping, `subPath`-mounted | `Works by default` | operator-native | Nothing to enable. The only ceiling is etcd's 1 MiB per ConfigMap, and `defaultMode` carries the permission bits. [row 4](#storage). |
| **Network restriction** — `restrict_to_network` | `spec.networkPolicy` / `spec.networkPolicyRef` — a per-workspace NetworkPolicy | `Needs cluster infra` | operator-native<br>agent baseline:<br>`networkPolicies.enabled=true` | The operator stamps the per-workspace policy with no configuration, but a policy is inert unless the CNI enforces NetworkPolicy — under Flannel or canal alone every rule is a no-op that silently succeeds. The full rule set, the podSelector-versus-namespaceSelector story, and the missing per-workspace egress IP are [row 5](#networking--access) · [how-to](howto/network-policy-enforcement.md). |
| **Named-network selection** — `restrict_network_names`, `allow_network_selection` | Nothing. A pod has one CNI attachment and no name to choose from. | `Not on Kubernetes yet` | not implemented | Docker named networks are an addressing construct; a NetworkPolicy is a filter, not a network, so [row 5](#networking--access) can restrict traffic but cannot offer a user a list of networks to launch into. Live evidence: the Kubernetes agent reports an empty network list to the manager (`servers.docker_networks = {}`), so the network selector has nothing to offer; NetworkPolicy provides restriction ([row 5](#networking--access)), not selectable named networks. What is missing is a network-attachment model — Multus with a secondary CNI, or an equivalent — which the operator does not implement. |
| **Egress gateways** — `override_egress_gateways` | `spec.cniEgress` — opaque endpoint config surfaced to the CNI chain by pod annotation | `Enable in chart` | `egressInstaller.enabled=true`<br>`egressInstaller.distro`<br>or<br>`egressInstaller.cniBinDir` | The CR field is only the request; the node-side half is the chained-CNI shim that enters the session's netns and brings the tunnel up there. Node prerequisites, the graceful-versus-crash lifecycle, and the older `spec.vpnSidecar` alternative are [row 6](#networking--access) · [how-to](howto/egress-installer-node-prerequisites.md). |
| **Web filtering** — `filter_policy_id`, `filter_policy_force_disabled`, group `web_filter_policy` | The squid adapter inside the session pod, pointed at the session-proxy Service | `Works by default` | operator-native (`podStartCommands`) | The agent substitutes the session-proxy Service address for the Docker agent's runtime IP discovery, so nothing has to be set. Enforcement is application-layer and inside the pod, which is its limitation. [row 13](#networking--access). |
| **Zone pinning** — `restrict_to_zone`, `zone_id`, group `allow_zone_selection` | The zone the `Agent` custom resource registers in | `Works by default` | `agent.zone` | One agent release is one zone. `agent.zone` must name a zone that exists on the control plane (`kasm-helm.kasmZones`), and the manager then routes zone-restricted workspaces to the agents in that zone. Several zones means several agent releases, one per zone, each with its own `agent.publicHostname`. |
| **GPU** — `require_gpu`, `gpu_count`, `gpu_graphics_acceleration`, `gpu_video_encoding` | `nvidia.com/gpu` in the pod's resource limits, plus `spec.devices` for the DRI nodes | `Needs cluster infra` | `gpuOperator.enabled=true`<br>`agent.gpu.enabled=true`<br>`agent.workspacesNodeSelector` | Compute (`require_gpu`, `gpu_count`) is [row 7](#gpu); graphics acceleration (`gpu_graphics_acceleration`, the EGL/DRI path) is [row 8](#gpu) · [how-to](howto/gpu-nodes.md). Allocation moves to kubelet's Device Plugin API, which is more robust than the Docker agent's own bookkeeping but removes the Kasm-level GPU metadata. `gpu_video_encoding` (NVENC) additionally needs the GPU driver stack present on the node and in the workspace image — unverified in this lab, which has no GPU nodes. |
| **Session time limit** — `session_time_limit`, and the group setting of the same name | Nothing. The manager expires the session and asks the agent to destroy it. | `Works by default` | manager / UI | Expiry is control-plane bookkeeping; the agent's part is the destroy, which is the same pod deletion any stop performs. What the cluster contributes is the shutdown budget: `stopTimeoutSeconds` on the CR (default 300) sets the pod's grace period, extended by 30s where a stop hook has to finish first ([row 10](#sessions--media), [row 19](#sessions--media)). |
| **RDP / RemoteApp** — `rdp_client_type`, `is_remote_app`, `remote_app_icon`, `remote_app_name`, `remote_app_program`, `remote_app_args` | The control plane's RDP gateways. These settings describe **Server** workspaces, not pods. | `Works by default` | `kasm-helm.components.rdpGateway.enabled`<br>`kasm-helm.components.rdpHttpsGateway.enabled`<br>`kasm-helm.directRdpService.enabled=true` | Both gateways ship as ordinary Deployments in the control-plane chart and are on out of the box; `directRdpService` is only for native-client access. The targets are Windows or Linux hosts **outside** the cluster — the gateway brokers to them and nothing here schedules a pod. [row 21](#networking--access). |

## 2. Group & session settings

`group_settings` is where nearly every session behaviour is decided, and most of it is negotiated
between the browser client, KasmVNC inside the workspace image, and the control plane — the
container runtime underneath is not part of that conversation. That is why so much of this section
is `Works by default`. The exceptions are the toggles that need a host device, a durable place to
put bytes, or an API the Kubernetes agent does not have.

| Setting(s) | On Kubernetes this becomes | Status | Provided by | Notes |
| ---------- | -------------------------- | ------ | ----------- | ----- |
| **Audio** — `allow_kasm_audio`, `kasm_audio_default_on` | Nothing cluster-side. Audio rides the session connection. | `Works by default` | control plane + KasmVNC | Playback is captured inside the session container and streamed to the browser, so no host sound device has to exist on the node and no chart value is involved. |
| **Microphone** — `allow_kasm_microphone` | A PulseAudio relay started inside the session pod | `Works by default` | operator-native (`podStartCommands`) | The operator injects `PULSE_RUNTIME_PATH` and mounts the PulseAudio runtime at `/var/run/pulse`; the workspace image supplies the binary. [row 12](#sessions--media). |
| **Webcam** — `allow_kasm_webcam` | A `/dev/video*` device from `v4l2loopback`, requested as the extended resource `kasm.com/video` | `Needs cluster infra` | `nodePrep.enabled=true`<br>`nodePrep.modules.v4l2loopback.enabled=true`<br>`videoDevicePlugin.enabled=true` | The one media toggle that changes the node: a kernel module has to be loaded and re-loaded after every reboot, and a device plugin has to advertise the result. Both halves are required, and the namespace has to permit the `privileged` Pod Security Standard. [row 9](#sessions--media) · [how-to](howto/kernel-modules-and-webcam.md). |
| **Clipboard** — `allow_kasm_clipboard_up`, `allow_kasm_clipboard_down`, `allow_kasm_clipboard_seamless` | Nothing cluster-side | `Works by default` | control plane + KasmVNC | Clipboard direction and seamless mode are client-and-image behaviour; the pod boundary is irrelevant to them. |
| **Uploads & downloads** — `allow_kasm_uploads`, `allow_kasm_downloads` | Nothing cluster-side | `Works by default` | control plane + KasmVNC | Transfers go over the session connection. Where the bytes land does matter: without a persistent profile ([row 2](#storage)) or a storage mapping ([row 3](#storage)) an uploaded file lives on the pod's ephemeral filesystem and dies with the session. |
| **Printing** — `allow_kasm_printing` | CUPS started inside the session pod | `Works by default` | operator-native (`podStartCommands`) | Entirely in-pod; the stock Kasm images ship CUPS and `kasm_printer_service`. [row 11](#sessions--media). |
| **Gamepad** — `allow_kasm_gamepad` (with `control_panel.advanced_settings.show_game_mode`) | Nothing cluster-side | `Works by default` | control plane + KasmVNC | Gamepad input is relayed by the browser client into the session. Unlike the webcam it needs no host device node, so it costs nothing at the cluster layer. |
| **Session sharing & casting** — `allow_kasm_sharing`, `shared_session_full_control`, `lock_sharing_video_mode`, global `cast/*` | Extra viewers on the same session, through the same session proxy | `Works by default` | control plane + KasmVNC | Shared and cast viewers connect through the session-proxy Service the owner already uses, so sharing needs no exposure beyond [row 20](#networking--access). Cast configurations are control-plane objects and can be seeded with `kasm-helm.kasmConfig.config`. |
| **Session recording** — `record_sessions`, with `session_recording/*` and `storage/object_storage_key`/`storage/object_storage_secret` | A recorder process in the session pod, uploading before the pod is allowed to terminate | `Partial` | operator-native (`podStartCommands`/`podStopCommands`) | Capture works and needs no values. The limitation is storage, not recording: nothing mounts a PVC at `/opt/kasm/recordings`, so an in-flight recording buffers on the pod's ephemeral filesystem and an evicted or OOM-killed pod loses it. The stop hook holds the pod open for the upload within `stopTimeoutSeconds` + 30s. [row 10](#sessions--media). As built in the fixed operator: `KasmWorkspace.spec.recordingBufferSize` (default `3Gi`) provisions an `emptyDir` with that `sizeLimit` at `/opt/kasm/recordings`, a `recorder-prep` init container pre-creates it for the recorder user, and the container's ephemeral-storage request/limit is seeded to cover it — verified live by patching a workspace (`KASM_SVC_RECORDER=1`, `1Gi` → mount + `2Gi` ephemeral floor). It bounds the buffer and survives container restarts, not pod loss; the manager only enables the recorder when a recording upload location is configured. |
| **SSH key injection** — `inject_ssh_keys` | A ConfigMap mounted at `/home/kasm-user/.ssh/`, with permissions fixed by a start hook | `Works by default` | operator-native | Rides the file-mapping path, then `chown`s to `1000:0` and `chmod 400`s the private key. [row 14](#security--policy). |
| **Container logging** — `enable_container_logging` (`enable_ui_server_logging` is control-plane-side and unaffected) | Nothing. The agent has no route to a container's logs. | `Not on Kubernetes yet` | not wired (operator/agent gap) | The agent's ClusterRole (`kasm-agent`) grants `pods` get/list/watch but no `pods/log`, so the Kubernetes agent cannot fetch container logs through the API server the way the Docker agent reads `docker logs`. Workspace stdout/stderr is still available as ordinary pod logs (`kubectl logs`) and via the cluster's log pipeline (see the [Telemetry row](#operations--platform) / `otelCollector`), not through the Kasm UI. |
| **Environment variables** — `expose_user_environment_vars` | `spec.env` on the `KasmWorkspace` | `Works by default` | operator-native | User and group environment variables are merged with the desktop variables the operator injects and become ordinary container env. |
| **Stop & delete** — `allow_kasm_stop`, `allow_kasm_delete`, `allow_kasm_force_delete` | Deletion of the `KasmWorkspace`: stop hooks from a finalizer, then the Deployment, Service and policy go | `Works by default` | operator-native | Deleting the CR runs `podStopCommands` from a finalizer inside the grace period ([row 19](#sessions--media)) — which is what gives an in-flight recording its chance to upload ([row 10](#sessions--media)) — and then removes the workload. A persistent profile PVC survives the deletion ([row 2](#storage)); force delete skips the wait. |
| **Pause** — `allow_kasm_pause` | Nothing. The workspace pod keeps running. | `Not on Kubernetes yet` | not implemented (operator gap) | Kubernetes has no container pause. Observed live: `pause_kasm` returns success and the manager marks the session *paused*, but the workspace pod is simply replaced and keeps running (`phase=Running`); `resume_kasm` then fails with "No resources are available to create the requested Kasm". Treat `allow_kasm_pause` as unsupported on the Kubernetes agent until the operator implements pause semantics (e.g. scale-to-zero + resume); disable it for groups that use Kubernetes agents. Re-tested on 1.1200.0-develop: identical pause behaviour (pod replaced and still running, manager shows *paused*), but `resume_kasm` now returns success — the 1.19.0 "No resources are available" resume error is gone; the session was simply never paused. |
| **Session lifecycle & limits** — `keepalive_expiration`, `keepalive_interval`, `keepalive_expiration_action`, `idle_disconnect`, `usage_limit`, `max_kasms_per_user`, `delete_anon_user_on_expiry_with_active_session` | Nothing. Manager-side accounting; the agent only ever receives a create or a destroy. | `Works by default` | manager / UI | The timers run on the control plane, with global counterparts under `scale/*` ([section 3](#3-global-settings)). The cluster's contribution is the shutdown budget the operator gives a terminating session. |
| **RDP client toggles** — `allow_login_kasm_rdp`, `allow_kasm_rdp_client_file_transfer_clipboard`, `allow_kasm_rdp_map_local_drives`, `allow_kasm_rdp_webauthn_passthrough`, `allow_kasm_smart_card_passthrough` | The control plane's RDP gateways | `Works by default` | `kasm-helm.components.rdpGateway.enabled`<br>`kasm-helm.components.rdpHttpsGateway.enabled` | These govern a native RDP client connecting to a **Server** workspace, not a container session, so they are settled entirely in the control-plane chart. [row 21](#networking--access). |
| **Authentication & accounts** — `allow_totp_2fa`, `allow_webauthn_2fa`, `require_2fa`, `allow_2fa_self_enrollment`, `require_subscription`, `password_expires`, `auto_add_local_users`, `auto_login_to_kasm` | Nothing. Entirely control plane. | `Works by default` | control plane | Identity is decided before a workspace exists, so none of it reaches the agent. SSO, LDAP and SAML configurations are seedable at database initialisation with `kasm-helm.kasmConfig.config`. |
| **UI & client preferences** — `control_panel.*`, `kasmvnc_mode_preference`, `enable_webp`, `default_ui_language`, `dashboard_redirect`, `default_image`, `show_disabled_images`, `disabled_image_message`, `display_ui_errors`, `session_banner`, `staged_session_language_and_timezone_preference_override`, `metadata`, `kasm_ime_mode_default_on` | Nothing cluster-side | `Works by default` | control plane + KasmVNC | Control-panel visibility, language, banners and error display are all UI state. `kasmvnc_mode_preference` and `enable_webp` select the streaming mode KasmVNC negotiates inside the session container — an image capability, unaffected by what runs the container. |

## 3. Global settings

The `settings` table is keyed by category and name — `auth/kasm_auth_domain`,
`scale/provision_timeout`, `logging/log_host`. Most categories are control-plane behaviour the
cluster never sees. The ones that matter here are the categories that describe *where the agent
is*, *what it may do*, and *who else is allowed to talk to it*.

| Setting(s) | On Kubernetes this becomes | Status | Provided by | Notes |
| ---------- | -------------------------- | ------ | ----------- | ----- |
| **Manager & agent registration** — `manager/agent_version`, `manager/token`, `manager/manager_expiration`, `manager/same_zone_reply`, `proxy/proxy_path`, `scale/auto_agent` | The `Agent` custom resource: the agent registers with the manager, heartbeats, and is issued a `serverID` | `Enable in chart` | `agent.manager.hostname`<br>`agent.manager.port`<br>`agent.manager.scheme`<br>`agent.manager.pathPrefix`<br>`agent.manager.existingTokenSecret`<br>or<br>`agent.manager.token`<br>`agent.publicHostname` | This is the join between the two halves and the first thing to get right ([row 1](#sessions--media)). The manager token is the shared secret both sides check — prefer `agent.manager.existingTokenSecret`, because a token set inline lands in the Helm release history. `agent.manager.pathPrefix` (`/manager_api` by default) is the client-side counterpart of `proxy/proxy_path`; set it empty only for direct manager-Service access. `manager/agent_version` gates which agent builds the manager accepts, so an image tag out of step with the control plane surfaces as a registration failure rather than a runtime error. |
| **Authorization domain & auth session** — `auth/kasm_auth_domain`, `auth/session_lifetime`, `auth/same_site` | The cookie scope the control plane hands the browser — which decides whether the session proxy's hostname is inside it | `Enable in chart` | `kasm-helm.kasmConfig.generatePreseed=true`<br>`kasm-helm.kasmConfig.authDomain` | The one auth setting with a genuinely Kubernetes-shaped consequence: the agent's session proxy is a **different hostname** from the control plane, so the session cookie has to be scoped to a domain that covers both or the browser drops it the moment streaming starts. Applied at database initialisation — fresh installs only; on an existing database change it in the admin UI under Settings → Auth. TLS for both hostnames is [row 22](#security--policy) · [how-to](howto/external-access-and-tls.md). |

## 4. Cluster infrastructure

The infrastructure layer the settings above point into. Each row here is a Kubernetes capability —
a device plugin, a CSI driver, a chained CNI shim, an ingress path, a privileged DaemonSet — that
one or more settings in sections 1 to 3 depend on, and each carries the cluster prerequisites and
the exact values that turn it on. These are the numbered rows the
[how-to guides](howto/README.md) reference, and their numbering is stable.

The columns change here because the question changes: not "what provides this setting", but "what
has to exist in the cluster, and what do I set to get it".

## Reading the matrix

A few things worth carrying away from the table as a whole:

- **`Works by default` is the largest group, and that is the point.** Printing, microphone, web
  filtering, SSH keys, file mappings, lifecycle scripts and node targeting are all handled by the
  agent and operator through `podStartCommands`, ConfigMaps and CR fields. They need no chart
  values because there is nothing for a chart to switch on.
- **The rows that cost you something are the node-level ones.** Webcam, WireGuard, Secure Boot and
  per-session egress all need privileged workloads, and every one of them requires the namespace to
  permit the `privileged` Pod Security Standard —
  `kubectl label namespace kasm-agent pod-security.kubernetes.io/enforce=privileged`.
  `egressInstaller` additionally needs host namespaces (`hostPID`, `hostNetwork`), which conflicts
  with any blanket `disallow-host-namespaces` policy.
- **Two values, not one, is a recurring pattern.** GPU (`gpuOperator.enabled` + `agent.gpu.enabled`),
  cloud storage (`csiRclone.enabled` + `agent.storageMappings.enabled`) and webcam
  (`nodePrep.*` + `videoDevicePlugin.enabled`) each need the infrastructure *and* the agent-side flag
  that makes Kasm ask for it. Setting one alone fails quietly.
- **[kasm-platform](../charts/kasm-platform/README.md) bundles all of this.** Every value above is
  reachable from the top-level umbrella by prefixing `kasm-agent.` or leaving `kasm-helm.` in place,
  so nothing here forces a split install.
- **Airgap.** Every chart installs with no internet access. Mirror the images first —
  `make images-agent` lists every image the agent manifests reference, and `make package-agent`
  builds the self-contained chart archive. The build-from-source paths in `kasm-node-prep` are the
  exception that needs planning: use `nodePrep.modules.v4l2loopback.method=kmm` with a pre-built
  image in your own registry rather than compiling on nodes that cannot reach GitHub. Details in the
  [kasm-agent README](../charts/kasm-agent/README.md).

## Source

The rows in sections 1 to 3 are the configuration surface of a live **Kasm Workspaces 1.19.0**
control plane, read from its own schema: the `images` table (workspace settings), `group_settings`
(group and session settings), and `settings` (global settings, keyed by category and name). What
each one becomes on Kubernetes is grounded in the agent operator's custom resource definitions —
`KasmWorkspace` and `Agent` — read from the API server of the cluster this repository is developed
against. Where a setting maps to a CR field, that field is named; where it maps to nothing, the row
says so.

The numbered infrastructure rows in section 4, their cluster prerequisites and the how-to guides
they link to began as Kasm's internal *Kasm Feature to Kubernetes Dependency Matrix*
(`k8s-feature-dependencies.md`); it is credited here as implementation notes for that layer, not as
the feature list. The chart and value mappings throughout are this repository's, verified against
each chart's `values.yaml`.

Every `Partial` and `Not on Kubernetes yet` row states a limitation that was observed on a running
session in the lab cluster, not inferred from the two systems' documentation. The exceptions, named
in their own Notes, are `gpu_video_encoding` (no GPU nodes in this lab) and the settings that never
reach the cluster at all.
